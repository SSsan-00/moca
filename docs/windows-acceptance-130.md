# Windows実機の受入検証（Issue #130）

Windowsの自動回帰、同じ実機でのブラウザ自動操作、Windowsデスクトップでの目視、認証済み実Junieによる受入は別の結果として記録する。テストでは架空の PHP / C# / Markdown だけを使い、実際の業務コード・本番チェッカー・フック・ビルドを実行しない。実行ログに認証情報・通知のURL・業務パスを載せない。

変更前の実機Chromeでは、390pxのときタブ選択インジケータが403pxまで一時的にはみ出す失敗を再現した。再読込が開始されず復旧画面の待ち合わせが失敗する試行もあった。修正後、同じ実機Chromeで設定・復旧・モーダルの試験が3/3回通過した。CIの必須検査は省略しない。

## 再現手順

通常のユーザーのPowerShellで、隔離したチェックアウトから実行する。Pythonのほか、対応するNode.jsとEdge/Chromeが必要。

~~~powershell
python -m pip install -e .
python tests/run_shard.py full --require-ui --timings
python tests/smoke_windows_junie.py
# 任意: rule-search の依存と所定のハッシュのE5ファイルを用意した場合
python tests/smoke_windows_rule_search.py C:\path\to\e5
python tools/windows_toast_smoke.py --interval 12 --timeout 48
~~~

通知確認ではブラウザを最小化し、「移行ハーネス」通知をクリックする。合成のRun B画面を開き、スクリプトが一致を出すことを確認。既定間隔の確認は引数なしで開始し、0・5・10分の表示を観察してからクリックする。「Windows API accepted」は画面に出たことの証明ではない。同じ通知タグが通知センター上では置換されることがある。実画面では、回答後の再通知停止、別Run・別タブ、古い通知、集中モードを使った抑制、通知に本文が含まれないことも記録する。

モデルを使う項目は、Junieで同じWindowsユーザーの利用可能なモデルを確認する。モデル・推論強度・対象コミットを固定し、設定箇所とACPネゴシエーションを記録する。初回と2ターン目について、スキルのコマンド公開と内蔵指示へのフォールバックを区別する。検索とトークン削減では比較対象以外を同じにし、必須規則、末尾の例外、優先順位、別画面の除外を独立した静的チェックで採点する。
