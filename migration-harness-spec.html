IMPLEMENTATION STATUS / DESIGN

PHP → C# 移行ハーネス

Windows上でローカル実行するPython + LangGraphのハーネス。現在は移行対象の準備と、文字数上限に合わせたコンテキストの分割・Junieへの順次入力を実装しています。ビルド、チェッカー、修正ループ、アンカーJSONレビューは今後の設計です。進捗画面のデモも確認できます。

前提

構成と移行先

PythonLangGraphJunie.NET 9

現在、LangGraphが設定検証・コンテキスト作成・worktree作成を管理し、その後PythonからJunie CLIをカプセルごとに順次起動します。JunieはdotUltimateなどで利用するエージェントです。移行先は既存のASP.NET Core Razor Pages（現状.NET 9）で、共通関数などは.csに配置します。

移行材料

  • 元のPHPと、コメントだけを追加した注釈版PHP
  • 別ツールが生成した仮C#
  • 独自移行ルールの該当箇所と必要最小限の既存C#例
  • 差分レビューに使うDiff ViewerワークスペースJSON

大規模コードへの対応

数百万行のリポジトリや数万行のファイルを丸ごとAIへ渡しません。アプリ用worktreeを1つ作り、Junieには対象箇所と必要な参照だけを入れた一時作業フォルダを渡します。

公開する範囲

公開するのは汎用ハーネスと設定例です。独自ルールMarkdown、利用者固有のスクリプト、アプリのソースや設定は利用者側で用意します。

LangGraphとチェックポイント

LangGraphは現在、準備フローを管理します。SQLiteチェックポイントも準備グラフの状態保存に使いますが、保存した状態から再開する機能はまだありません。Junie実行以降は現在LangGraphのグラフ外で動きます。

参照範囲の制限

ハーネスは指定した資料だけをコンテキストにまとめ、Junie用フォルダには対象ファイルとコンテキストだけを置きます。これはハーネス上の範囲指定であり、別の絶対パスへのアクセスをOSレベルで遮断するものではありません。

現在の文字数上限

max_context_charsの既定値は100,000文字です。1回分のコンテキストが上限を超える場合、原文を切り捨てず、現在は行境界で複数カプセルに分割して順にJunieへ渡します。関数や制御構文の境界を判定する機能は未実装です。極端に長い1行は文字位置を記録して分割し、隣接断片の前後512文字（上限の小さい設定では5%）を読み取り用に重ねます。AIにはfocus範囲のみを移行し、重なり範囲は文脈参照に限るよう指示します。文字コード・文字数・元の行範囲・focus範囲・重なり範囲はcapsule/manifest.jsonに記録します。入力はUTF-8 BOMを優先し、BOMなしはUTF-8とEUC-JPを厳密に判定します。両方で異なる文字列になる曖昧な入力や、どちらでも読めない入力は自動選択せず、設定で文字コードを指定します。対象ファイル全体や会話履歴・ツール出力は計上しません。

進捗の配信

Python標準ライブラリのHTTPサーバーを127.0.0.1で起動し、ブラウザーの標準EventSource APIへSSEで状態とログを送ります。SSEは一方向の配信に使い、WebSocketは使いません。

画面からの操作

一時停止・再開などの頻度が低い操作はHTTP POSTで送ります。WebSocket用ライブラリなど、追加のPythonパッケージは導入しません。

再接続と履歴

イベントは画面に送る前に実行記録へ保存し、連番IDを付けます。接続が切れても、再接続時に最後に受信したID以降を再送できるようにします。

公開デモとの違い

公開中の進捗画面は模擬データを表示するHTMLです。実際のハーネス、Junie、ビルド、チェッカーとの接続は今後の実装です。

台帳の単位（案）

PHPの関数・メソッド・ページ処理など、意味のまとまりを1項目にします。構造を判定できない場合は、設定したファイルと行範囲を使います。行番号だけに頼らず、ファイル・シンボル名・該当範囲を併記します。

状態（案）

未処理、移行候補あり、確認済み、対象外（理由付き）、人の判断待ちを区別します。未処理や判断待ちが残る項目は完了扱いにしません。

依存情報の取得

呼び出し先、include、共通関数、既存C#例、該当ルールを関係情報から探し、必要な原文を追加で渡します。要約は索引として使い、原文の代わりにはしません。

移行先との対応

各入力項目に対して、移行先ファイル・シンボル・範囲と対応の根拠を記録します。チェッカーなどで行番号がずれた場合も、シンボルや内容を合わせて追跡します。

現在実装した上限超過対応

指定範囲を行境界で分割し、複数カプセルを順番にJunieへ渡します。関数・制御構文の境界を安全に判定できる機能は未実装のため、現在は行単位です。極端に長い1行は文字位置で分割し、前後の重なりを付けます。各断片のfocus範囲と参照用の重なり範囲はmanifestに残します。依存情報の追加取得、台帳・網羅性確認は今後の設計です。対象ファイル全体のサイズは現在の上限に含まれません。

チェッカーの偽陽性

チェッカーのテキスト出力を保存します。ルールIDとファイル名を主な手掛かりにし、ずれる可能性がある行番号だけで指摘を特定しません。人が許容した指摘は理由とともに記録します。

4. 今後追加するアンカーJSONレビュー（未実装）

既存JSONから対応情報を読む

ハーネスがファイル順、ファイル名、segments、既存アンカーを読み取ります。ワークスペースJSON全体はAIに渡しません。

AIがアンカー案を作る

対象コードと必要な周辺行だけを使い、根拠がある対応行を提案します。曖昧な行は無理に結びません。

JSONを検査する

Diff Viewerのエクスポート形式に合わせ、ファイル対応、行番号範囲、行の順序を確認してから読み込みます。候補の根拠は別の実行記録に保存します。

Diff Viewerで人が確認する

ソースは読み取り専用で参照し、アンカーだけを調整します。ソースコードの修正が必要ならViewerを離れ、ハーネスの修正・検証フローへ戻します。

Viewerではソースを変更しない

Diff Viewerはソース参照とレビュー補助に限定します。保存なしで開き、エディタ本文は編集・保存しません。変更してよいのはアンカー設定だけです。出力はレビュー済みアンカーJSONとレビュー判定・理由に限ります。

レビュー後に保存するもの

レビュー済みアンカーJSON、ファイル対応情報、ビルド・テスト結果、チェッカー出力、人が許容した指摘と理由を移行単位ごとに保存します。ソースの差分はアプリ用worktreeから参照し、Viewerから書き戻しません。
