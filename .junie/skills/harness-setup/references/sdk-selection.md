# 既存の.NET SDKを使う

SDK 9以降が導入済みで、SDK選択に成功している場合はそのまま使う。既存のSDK指定がある場合や選択に失敗した場合に、この手順を使う。

SDK不足の相談では、アプリの `global.json` を直接開いて `sdk.version` を確認する。ファイル検索に出なくても、利用者が場所を示していればそのファイルを読む。見つからない場合は内容を利用者に確認する。

## SDKの選択はdotnetで確かめる

PowerShellで、アプリのルートを作業場所にして確認する。

```powershell
Push-Location -LiteralPath 'C:\work\LegacyApp'
dotnet --list-sdks
dotnet --version
Pop-Location
```

`--list-sdks` はインストール済み一覧、`--version` はその場所で選択できるSDKを示す。成功した場合は、その結果を使う。バージョン番号から独自に互換性を推測しない。`Pop-Location` で元のハーネスのフォルダに戻ってから `.\h.cmd d` を使う。

互換SDKがない場合、`dotnet --version` は通常「対応するSDKが見つからない」というエラーになる。たとえば8.0.100指定・ロールフォワード未設定で10.0.201しかなければ、10.0.201が表示されるという説明にはしない。逆にコマンドが成功して想定外の版を表示したら、作業場所と有効な `global.json` を確認する。**利用者からまだ出力を受け取っていない場合は、結果を断定せず確認コマンドを案内する**。

**既存SDKで選択・ビルドできる場合は追加導入しない**。`net8.0` のようなTargetFrameworkの値だけでSDK 8の追加を要求しない。SDKの選択と、アプリが対象とするフレームワークは別の設定である。

有効な `global.json` の条件を満たすSDKがないと確認できた場合に追加するSDKは、**`global.json` の `sdk.version` に書かれた完全な版番号をそのまま案内する**。たとえば指定が `8.0.100` なら「.NET SDK 8.0.100」とし、「8.x」「8.0.400」「最新LTS」に置き換えない。既存の `version` や `rollForward` は保持する。

指定版を入手できない場合やSDK更新を希望する場合は、アプリのSDK更新として別途検討する。導入を進めるためにロールフォワード条件を緩めたり、未確認の代替版を勧めたりしない。選択規則の詳細は [Microsoftの仕様](https://learn.microsoft.com/en-us/dotnet/core/tools/global-json) を参照する。

`global.json` がない、またはSDK版が指定されていない場合は、既存SDKを選択し、ビルド対象プロジェクトの要件を確認する。新しいSDK固定ファイルは作らない。情報がない段階でSDKの具体的な版を決めない。SDKが選べても、ビルドやパッケージ復元の成功とは別なので、これらは移行・検証工程で確認する。

SDK未導入でもハーネスの設定と準備は進められる。準備用スクリプトがSDKを使う場合だけ、先に導入する。
