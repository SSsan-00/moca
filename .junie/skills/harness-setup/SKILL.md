# Windowsで移行ハーネスを設定する

[Windowsユーザーマニュアル](../../../docs/windows-user-guide.md) を読み、利用者が依頼した到達点まで支援する。初回は設定を保存し、ドライランで実行計画を確認する。移行を依頼されていなければそこで止める。案内だけの依頼ではファイルを変更しない。**未実行の設定保存・検証・移行・SDK確認を「確認済み」と報告しない**。資料から判明したこと、実行結果で確認したこと、これから行う操作を区別する。

利用者の開発環境には **.NET SDK 9以降が導入済み** として、使える既存SDKを再利用する。通常の導入でSDKを追加・再インストールさせない。これは利用者環境の前提であり、ハーネスがSDK 9未満を禁止する仕様ではない。

## ルール整理を依頼された場合

散在するルールの整理や、**プロジェクト共通の移行ルールの読み込み方**を最適化する依頼は、[harness-optimize-rules](../harness-optimize-rules/SKILL.md) を読んで進める。既存設定なら `/harness-optimize-rules harness.local.toml の移行ルールの読み込み方を最適化して設定へ反映してください` と呼び出せる。原文を整理する場合の保存先はハーネス側の `rule-workspace/<project>/`。必須事項を保持し、詳細には具体的な読む場面を設定する。全行の保持と適用範囲・優先順位等の意味レビューが済むまで新ルールを有効化しない。`Agent.md` はファイル名だけで必須にはならず、`required` として登録する。

案内だけならTOMLを変更しない。設定反映も依頼されていれば同スキルの手順で対象の旧ルールだけを置き換える。生成される `rules.toml` は断片であり、設定全体を上書きしない。**ルール整理・設定確認だけのために新規Runを開始しない**（登録済みスクリプトが動く）。

## 先に確認すること

既存の `harness.local.toml` があれば読み、次の各項目を点検してから設定案を出す。設定例は [harness.example.toml](../../../harness.example.toml)。相対リンクが見つからない場合はハーネスのチェックアウト先を確認する。

| 点検するもの | 判断と案内 |
| --- | --- |
| `target` / `targets` | **Razorの `.cshtml` と `.cshtml.cs` は両方必須**。片方しかない設定は保存できない。不足する相方の具体的なパスを示し、移行先欄に追加する。**移行先は新規ファイルでもよく、空ファイルの事前作成は不要**。 |
| `global.json` と `dotnet --list-sdks` | アプリの場所で `dotnet --version` を確認し、成功すれば選択済みSDKを使う。既存の `global.json` に指定がある場合や選択に失敗した場合は [SDKの選択手順](references/sdk-selection.md) を読む。不足が確認できた場合だけ追加SDKを案内する。**`global.json` の変更は案内しない**。SDK更新を依頼された場合は別途扱う。 |
| `git status --short` と基準コミット | ビルド対象・依存ソース・チェッカー・準備後以降のスクリプトは基準コミットに必要。未追跡や未コミットの変更はworktreeに入らない。**PHP原文・参照資料は準備時の指定ファイルから読み、未コミットの内容も使える。これらのcommitを準備の必須条件にしない。** |
| Python | **3.11以上なら使用可**。3.13などがあれば3.11を追加しない。`py`がなくても `python --version` が条件を満たせば使える。既存チェッカーのPython指定は、必要なパッケージも含めて別に確認する。 |
| 既存環境 | 設定、`.venv`、Runを保持する。設定例で上書きしない。`.venv`が壊れている場合はエラーの原因を確認して修復方法を示す。準備済みworktreeは後からアプリ側をcommitしても更新されない。 |

アプリがGitリポジトリでも、初回コミットがなければ準備できない。`git -C "アプリのパス" rev-parse --verify HEAD` で確認する。必要なファイルの採用版を確認し、利用者の依頼範囲外のcommitや `git add .` は行わない。

## 導入する

- OS・シェルと、ハーネス・アプリの場所を確認する。読み取れる情報は調べ、不明な必須項目だけ尋ねる。Windowsへアクセスできない場合は利用者のコマンド出力で判断し、別OSの実行をWindowsでの成功扱いにしない。
- 同じPowerShellで `py -3 --version`（なければ `python --version`）、`git --version`、`junie --version`、`dotnet --list-sdks` を確認する。SDKは導入済みとして扱い、その他の不足ツールはマニュアル第1節の公式導入先へ案内し、導入後はPowerShellを開き直して再確認する。
- **設定の保存・検証はPythonとGitで進められる。実際の移行にはログイン済みJunieと.NET SDKも必要**。Runtimeだけではビルドできない。登録済みスクリプトの実行環境も確認する。Junieのバージョン表示はログインの証明にならない。認証は本人の端末・ブラウザーで行う。
- アプリのSDK指定が未確認なら、特定のSDKの版を推奨しない。`global.json` とビルド対象を確認する間も、Python・Gitの導入やダッシュボード設定は進められる。
- **設定確認までの依頼なら、SDKの導入や移行は別の作業とする**。ドライランはSDKや登録済みスクリプトを起動しない。アプリ側を調べるコマンドとハーネスを起動するコマンドの作業場所を混同しない。Gitは `git -C`、SDK確認は参照手順の `Push-Location` と `Pop-Location` を組で使う。
- マニュアル第1節の手順でclone、仮想環境、`pip install -e .`、ダッシュボードの起動を順に確認する。既に済んだ段階は繰り返さない。仮想環境のPythonを直接呼ぶので、`Activate.ps1` や実行ポリシーの変更は不要。ハーネスのフォルダで `.\moca`（[moca.cmd](../../../moca.cmd)）を引数なしで起動する。ブラウザーが開かなければ、表示されたURL全体を開く。初回は設定ファイルのコピーも不要。

## フォームに設定する

マニュアル第2節の項目に、確認できたアプリルート、保存先、機能名、元PHP、移行先、ビルド対象を対応させる。パスを推測で確定しない。PHPだけのリポジトリなら、`dotnet build` できる移行先プロジェクトの雛形が必要と伝える。

**設定 → プロジェクトの詳細設定** にリポジトリ、保存先、基準リビジョン、Junieのモデル・推論の強さ・ステップ数上限、ビルド・チェッカー、差分ビューアーがある。worktreeとRunの保存先は両リポジトリの外、互いに入れ子にしない。パスは絶対・相対のどちらでも指定できる。空白を含めてもフォームでは引用符を付けない。

モデルや推論の強さの指定が必要な場合は **Junieで使うモデル** と **推論の強さ** で選ぶ。希望がなければ既定値を使う。候補はJunie CLIから取得するが、利用には対応するログイン・契約が必要。一覧を取得できなければCLIを確認して **読み込み直す**。強さを指定するときはモデルも必要で、対応値はモデルごとに異なる。設定タブの変更は新規Run用。既存Runの次のJunie処理から変更する場合は、進捗の **Junie に指示** などでそのRunのモデル・強さを選んで保存する。詳細はマニュアル第2節を参照する。

- アプリのリポジトリ、作業ツリー・実行データの保存先、`diff_viewer.anchor_reference` の相対パスは**設定ファイルの場所**が基準。
- 移行元、ルール、参考実装、差分ビューアーHTML、仮C#のコピー元の相対パスは**アプリルート**が基準。外部ファイルの絶対パスも使える。`source` は拡張子なしを含め、拡張子を問わず移行元PHPとして全文を読む。
- 移行先、ビルド対象、仮C#のコピー先はアプリルートからの相対パス、または**アプリリポジトリ内の絶対パス**に限る。worktree内のパスへ正規化され、元のリポジトリには書き込まない。

ルール・参考実装・チェッカー・スクリプトは案件にあるものだけ追加する（マニュアル第3・4節）。ルールは全文をRunに固定する。「毎回適用する必須事項」は全文をJunie起動時の指示に渡し、「必要時に読む詳細・例」は「読む場面・内容」を基に必要時に原文を読む。旧設定は必須事項。自動で要約・分類しない。説明や例が長ければ別ファイルに分け、必要時の詳細として登録する。参考実装は全文をRunに固定してJunieが関連範囲を読む。コマンドは実行ファイルと引数を1行に1つずつ入力する。自動修正の空欄は2回、0は修正なし。カプセルの文字数上限は空欄なら250,000文字。差分ビューアーも任意で、未使用ならHTMLは空欄にする。**アンカーの参照JSON（任意）** はJunieの対応行の手本にするDiff ViewerワークスペースJSON。1行に1ファイル指定し、各ファイルの先頭12件までの手動アンカーを使う。空欄なら手本なしで今回の比較から提案する。同じRunから過去の対応例を補うことはない。指定ファイルがない・JSONが不正な場合はエラーになる。パスやJSONを修正するか、空欄に戻して保存するよう案内する。このセットアップスキルは移行用 `agent-workspace` には引き継がれない。

チェッカーの `py` を `python` や `python.exe` のパスへ変更する場合は、ランチャー用の `-3` / `-3.11` なども取り除く。`python -3.11` というコマンドにはしない。

## 設定の検証・新規実行・再開を案内する

**設定を保存** が成功したら、依頼に応じて **実行** タブで操作を選ぶ。

| 目的 | 操作 | 起きること |
| --- | --- | --- |
| 設定だけ確かめる | 移行単位を1件選び **設定を検証** | 基準コミット、入力、実行予定のコマンドと場所を表示する。Runもworktreeも作らず、準備スクリプト・Junie・ビルド・チェッカーは実行しない。「未確認」は実行時に確かめる項目。 |
| 新しい移行を始める | 移行単位を選び **選択したN件を実行**（未選択時は **選択した単位を実行**） | 新規Runを開始する。設定済みの準備前スクリプトを実行し、worktreeとカプセルを作成する。準備後スクリプトを経てJunie・ビルド・設定済みチェッカーへ進む。 |
| 中断したRunを続ける | 実行一覧で対象Runの **再開** | 同じRun IDの保存版から続ける。移行途中なら完了済み区間を飛ばし、移行済みなら保留中の編集を確認してビルド・検証へ進む。 |

新規実行は最大5件が並列で、残りは待機する。設定変更は実行中・待機中のRunがなくなってから行う。実行した場合は、進捗画面のRun IDと工程、保存先の `run.json`・`capsule/manifest.json`・worktreeを確認する。ドライランの成功を移行・ビルドの成功として報告しない。

再開の開始工程を指定する場合は、実行一覧の **再開方法…** で **移行から**・**ビルドから**・**チェッカーから** を選び、**計画を確認 → 再開する**。チェッカーからの再開には、保存済みのビルド入力と成果物の版が一致している必要がある。worktree作成前の失敗や移行元PHP・基準コミットを変更したい場合は、新しいRunを実行する。

Junieの作業フォルダー確認・操作許可はブラウザーのダイアログで対象パスを確認して回答する。中断しただけで自動修正の回数は消費しない。詳しくはマニュアル第5節を参照する。

Junie起動時にファイルが見つからない場合は、表示された `Executable`、`Command`、`CWD` と例外の詳細を確認する。`.BAT`／`.CMD` は対応済みなので、その拡張子だけを原因と決めつけない。PATHやインストールを直した後はPowerShellを開き直し、同じRunを再開する。起動できなかった修正試行は回数に含めない。

## 回答を出す前の確認

- SDKの実測が提示されていない場合、アプリでの `dotnet --version` の確認操作を回答に含める。選択できる既存SDKの追加・再インストールは案内しない。
- SDK指定の不一致は、指定に合うSDKの追加で扱う。`global.json` の削除、`sdk.version` の変更、`rollForward` の緩和を代替案に含めない。
- 設定変更はダッシュボードのフォームへ案内する。依頼されていないTOML編集に置き換えない。ビルド用ファイルの未コミット状態も点検する。
- 再開だけの依頼では既存環境を使い、エラーがなければ `pip install` を繰り返さない。
