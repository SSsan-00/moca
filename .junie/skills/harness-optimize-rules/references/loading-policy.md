# プロジェクト共通のルールの読み込み方を見直す

「プロジェクト共通の移行ルール」の **読み込み方** はTOMLの `usage`、**読む場面・内容** は `description`。ファイルを分割するだけでなく、この設定まで最適化する。必須本文を減らすために義務を読み飛ばさせない。

## 1. 設定から全ルールを棚卸しする

既存TOMLの `[[project.migration_rules]]` を読み、登録位置・解決後のパス・現在の `usage`・`description`・文字コードを記録する。`usage` 省略時は **required**。`[project].root` の相対パスは設定ファイルの場所、ルールの相対パスはアプリルートが基準。絶対パスも受け付ける。

旧形式の `[[units.inputs]]` に `role = "migration_rules"` があれば、それも全移行単位に共通適用される。見落とすと詳細に変更した同じ資料が必須として残る。旧形式の登録位置も記録し、同じファイルの読み込み方を整合させる。PHPや参考実装など別roleは変更しない。

既存設定の確認はハーネスにインストール済みのPythonで次の順に行う。過去の記録がある場合は新しいPACKを使う。**全ページの確認が通るまで分類・分割の計画や設定案を作らない。使用中のTOMLはヘルパーの `apply` だけで更新する。**

```text
python tools/rule_review.py start rule-workspace/LegacyApp harness.local.toml
python tools/rule_review.py read rule-workspace/LegacyApp 1 2
```

`start` は `config.before.toml` に設定のバックアップ、`loading-before.json` に原文のハッシュ付き棚卸しを保存し、全ページの一覧を表示する。この2ファイルを再作成せず、そのまま確認と設定反映に使う。**最大2ページずつ表示された本文を読み、各ページの終端まで確認する。** 最初が1ページだけなら `read` にはその番号だけを指定する。ツール出力が省略されたら該当ページを単独で読み直す。ヘッダーやキーワード検索だけで判断しない。

**読んだ束の全ページを `record PACK JSON --next` で記録する。** ヘルパーが検証して `reading-review.json` に追記し、続けて次の未読2ページを表示する。この出力を確認して再び記録するため、次の束の `read` 呼び出しは不要。過去の記録の再出力や転記用スクリプトも不要。未記録の束があると次へ進めないが、引用を確認するための再読はできる。最後に新しいページが表示されなくなったら `check` に進む。

```json
{
  "1": {"end": "ページ内で最後の空白でない原文行（行番号を除く）", "note": "この範囲の条件・義務・例外の要点", "required_lines": [12]}
}
```

`required_lines` には、そのページで確認した全体向けの義務や適用範囲が曖昧な規約の原文行番号を入れる。該当行がなければ空配列。ページをまたぐ条件や例外は続きも読んでから判断し、必要なら前の記録を補う。読み取りと記録は内容の確認を伴う。記録をファイルから自動生成しない。

例（1ページだけの束の場合。2ページなら両方の記録を渡す。引用・要点・行番号は実際に読んだ内容にし、JSONはシェルに合わせて引用する）:

```text
python tools/rule_review.py record rule-workspace/LegacyApp '{"1":{"end":"最後の原文行","note":"このページの適用条件・義務・例外","required_lines":[]}}' --next
```

WindowsなどでJSONの引用が扱いにくい場合は、読んだ束の記録だけをUTF-8の `batch-review.json` に書き、`record PACK "@batch-review.json" --next` で渡せる。既存の全記録を書き直す必要はない。確認済みの記録だけを訂正する場合は `--next` を付けない。

`read` の出力をリダイレクトして隠したり、多数のページをループでまとめて取得したりしない。`record` が引用違いを示したら該当ページを再読して訂正する。意味の確認をせずに原文から引用・要点を一括生成して検査を通さない。

```text
python tools/rule_review.py check rule-workspace/LegacyApp
```

未取得ページ、末尾の引用や要点がないページ、確認開始後に変わった設定・原文がある場合は先へ進まない。機械検証はページと記録の対応を確認する。意味の判断は本文のレビューで行う。

## 2. 原文の内容で分類する

| 内容 | 読み込み方と扱い |
| --- | --- |
| 全移行に適用する義務・禁止・優先順位、他の詳細を選ぶ判断基準 | `required`。入口のAgent.mdや既存の共通規約に残す。 |
| DB、帳票、Razorなど、適用条件が明確な処理の詳細・例 | `reference`。その処理に該当する場合は必ず原文を読む条件を付ける。「任意に守る」という意味ではない。 |
| 全体の義務と特定用途の長い詳細が同居 | スキル本文1〜3の手順で全行を保持して分割し、必須をAgent.md、詳細をreferenceにする。ファイル全体をreferenceへ落とさない。 |
| 適用範囲が曖昧、条件と義務を分離できない | `required`のまま保持する。短縮だけを目的に推測しない。 |
| 現在referenceだが全体の義務が含まれる | 必須側へ戻す。必要なら分割する。入力が増えても読み落としの防止を優先する。 |

ファイル名や長さだけで決めない。今選択中の移行単位で使わない資料も、別の移行や修正で必要なら登録を保持する。意味の同じ文が重複していても、原文を削って最適化しない。

すでに内容が分離されているファイルは、元のパスと本文を維持して分類だけ変える。空のAgent.mdを作ったり、整理済みファイルを名前だけで改名・再生成したりしない。既存のAgent.mdがあれば必須扱いを確認する。

**全登録の棚卸しと、分割対象の選択を分ける。** 既存登録をそのまま残すファイルは、分割用の `sources/`・`plan.json` に含めない。新しいAgentにも同梱すると、旧登録との二重読み込みになる。原文に元から存在する重複表現の保持とは区別する。

## 3. 詳細を読む条件を具体化する

`description` は、**対象の処理・読む場面・扱う内容**が分かる短い索引にする。「必要時」「詳細」「参考資料」だけでは選べない。移行元・移行先の処理だけでなく、ビルドやチェッカーの指摘から修正する場面も含める。原文にない条件・義務・話題を加えたり、適用範囲を狭めたりしない。以下の例をそのまま転用せず、索引に挙げた内容が実際の本文にあることを照合する。

例（原文にDB更新失敗時のrollbackと参照専用処理の例外がある場合）: 「DBの更新・参照処理を移行または修正するとき。rollbackと参照専用処理の例外を確認する」

すべての詳細を「毎回読む」とすると全文読み込みと同じになる。用途に該当する場合や適用判断がつかない場合に原文を読む案内にする。既存の説明が具体的で正しければ変更しない。説明文だけで規約を守ったことにはならない。

ハーネスは該当する詳細を選び、必須事項とともに原文を起動時に渡す。Agentの案内では提供済み本文の確認と、未提供の詳細ファイルの取得を区別する。確認済みの記録だけを目的とする再読や、除外された無関係な詳細の探索を指示しない。既存ルールの適用義務や原文は変更しない。

## 4. 反映し、設定と本文を照合する

意味レビューと原文・出力の照合はスキル本文に従う。案内だけの場合も、分類案は全ページ確認後に示す。反映を依頼された場合は、`config.before.toml` を元にPACK内へ `config.proposed.toml` を作り、対象のルール登録だけを編集する。相対パスは元の設定ファイルの場所を基準にしたままにする。既存のコメントも維持する。分割した場合は先に `rule_pack.py verify` を実行して全行の対応を確認する。矛盾や未解決事項があれば反映を保留する。

```text
python tools/rule_review.py meaning rule-workspace/LegacyApp rule-workspace/LegacyApp/config.proposed.toml > rule-workspace/LegacyApp/meaning-review.json
# Fill the evidence and unresolved findings before invoking apply.
python tools/rule_review.py apply rule-workspace/LegacyApp rule-workspace/LegacyApp/config.proposed.toml
python tools/rule_usage.py harness.local.toml --output rule-workspace/LegacyApp/loading-after.json
```

`meaning` は候補の版と原文→配置先の行対応を出力します。出力後、`meaning-review.json` の `entries` に、実際に照合した判断を次の形で記録してください。 `kind` は `obligation`（義務）、`condition`（適用条件）、`exception`（例外）、`priority`（優先関係）、`description`（読む場面）のいずれかです。読む場面には候補TOMLと同じ `description` も記録します。変更した配置先ごとに根拠を記録します。適用条件・例外・優先関係では `related` で結び付ける別の原文行と配置先を示します。ハーネスは参照が同じ資料内に実際に残る場合だけ反映します。同時提供の保証がない別資料への分割は保留し、見つかった矛盾・不足は `unresolved` に残します。確認のためだけにハッシュや引用を機械生成して済ませないでください。

```json
{
  "kind": "exception",
  "reason": "失敗時の例外は義務がある同じDB資料に残した",
  "source": {"path": "原文の絶対パス", "line": 18, "quote": "原文の18行目"},
  "destination": {"path": "生成ファイルの絶対パス", "line": 9, "quote": "原文の18行目"},
  "related": {
    "source": {"path": "原文の絶対パス", "line": 17, "quote": "原文の17行目"},
    "destination": {"path": "生成ファイルの絶対パス", "line": 8, "quote": "原文の17行目"}
  }
}
```

`apply` はレビューがない、候補や原文の版が違う、引用と実際の配置が一致しない、未解決事項が残る場合は使用中のTOMLを変更しません。この確認は、記録されなかった矛盾まで見つけるものではありません。設定と原文の版に結び付いた人またはJunieの意味レビューは引き続き必要です。

`apply` は全ページの確認を再検証し、確認記録にある必須行が必須登録に原文のまま残ること、対象外の設定が同じこと、設定案が読み込めることを確認してから反映する。分割時は、置換する原文と分割元の一致、生成ファイルの検証、必須・詳細の登録も照合する。失敗した場合は原因を解消するまで使用中のTOMLを直接編集しない。

必須事項がrequiredに残り、詳細のreferenceと説明が揃い、旧形式の同じ資料がrequiredとして残っていないか確認する。分割した原文の旧登録が、新しいAgentや詳細と重複して残っていないことも対応表と照合する。編集は生TOMLの対象箇所に行い、正規化済み設定でファイル全体を置き換えない。

ダッシュボードで案内する場合は **設定 → プロジェクト共通の移行ルール** で、必須は **毎回適用する必須事項**、詳細は **必要時に読む詳細・例** と **読む場面・内容** を指定する。新設定は次に準備するRunから有効で、保存済みRunの資料は変更しない。

結果には、各登録の読み込み方の変更、読む場面、判断理由と、2つの記録の `required_chars` をそのまま示す。分割した場合、元ファイルと出力の関係は1対1とは限らない。`coverage.json` の `placements` を使って「元ファイル・行範囲 → 配置先」を示し、TOMLの記載順から対応を推測しない。

ファイル名から分類を推測したり、編集後の分類で編集前の値を再計算したりしない。この文字数にトークン総量や速度の保証はなく、ハーネスが加える索引・会話履歴・ツール出力は別に増える。必須事項が多ければ無理に削減せず理由を伝える。
