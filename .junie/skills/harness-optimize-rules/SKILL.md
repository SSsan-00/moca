# 移行ルールを全行保持して整理する

ハーネスのチェックアウトで作業する。原文を要約・書き換えず、毎回適用する義務と必要な場面で読む詳細を分ける。`Agent.md` は必須事項、`details/*.md` は用途が明確な詳細・例とする。**ファイル名だけで必須扱いにはならないため、`usage = "required"` として明示登録する。**

## 依頼に合わせて進める

- **既存設定の読み込み方を最適化する**: [読み込み方の見直し](references/loading-policy.md) を読み、TOMLに登録済みの全ルールをページごとに確認し、`rule_review.py check` が通ってから分類する。使用中のTOMLの更新は `rule_review.py apply` を使う。すでに内容が分離されていれば `usage` と `description` だけを見直し、下記1〜3のファイル分割は不要。必須と詳細が混在するファイルだけ分割する。
- **まとまっていない原文を整理する**: 下記1〜3で `tools/rule_pack.py` による全行保持の分割を行う。新しい登録も [読み込み方の見直し](references/loading-policy.md) の分類基準で判断し、4で設定を案内・反映する。

既存設定を見直す入力例:

```text
/harness-optimize-rules harness.local.toml の「プロジェクト共通の移行ルール」の読み込み方を最適化して、設定へ反映してください。必須事項を残し、必要時に読む詳細には読む場面を設定してください。
```

Junieの入力例（シェルのコマンドではない）:

```text
/harness-optimize-rules C:/migration/loose-rules の全ルールを、情報を落とさず Agent.md と用途別の詳細へ整理してください。
保存先は rule-workspace/LegacyApp、既存設定は harness.local.toml です。TOMLは変更せず設定方法を案内してください。
```

整理・案内だけなら既存設定を変更しない。「設定を最適化して」「反映して」は設定編集の依頼として扱い、検証と意味レビュー後に4の手順で反映する。**同じ対象に両立しない指定がある場合、TOMLへの反映は保留する。原文を両方残すことと、矛盾の解消は別である。** 設定確認だけのために `prepare`・`run` を実行しない。準備前・準備後などのフックが動くためである。

## 1. 入力を固定する

- 対象の原文、既存設定、ハーネスの場所を確認する。指定された全入力テキストを棚卸しし、重複した内容も除外しない。**コピー元の絶対パス → `sources/` 内の相対パスと元バイトのSHA-256**をPACK内に記録する。ヘルパーはコピー元の場所を自動取得しない。
- 通常の保存先は `<ハーネス>/rule-workspace/<project>/`（以下 `PACK`）。アプリやRunの `agent-workspace` とは分ける。既存PACKを再利用するときは固定済み入力・成果物を上書きしない。
- **全入力を `PACK/sources/` に実ファイルとしてコピーし、元ファイルも残す。** 同名ファイルはサブフォルダ等で区別する。BOM・CRLFを含む元バイトを保持し、シンボリックリンクは使わない。コピー後の原文は変更しない。
- 対応する入力は **`.md`・`.markdown`・`.txt` のUTF-8（BOMありも可）テキスト**。他の拡張子のテキストは内容を変えず `.txt` 等のコピーにして対応を記録する。バイナリ・非UTF-8・シンボリックリンクは拒否される。非UTF-8は文字コードを確認し、元ファイルを `sources/` の外に保持して**追加のUTF-8コピー**を明示的に作り、変換前後のハッシュと方法を記録する。PDF等は形式に合う抽出が必要であり、抽出前の内容まで「無損失」と主張しない。検証対象の限界を報告し、未処理の入力を黙って落とさない。

ハーネス直下で、使用可能なPython 3.11以上を使う。Windowsで仮想環境を使う場合は `python` を `.\.venv\Scripts\python.exe` に置き換える。

```text
python tools/rule_pack.py snapshot rule-workspace/LegacyApp
```

`snapshot PACK` は `sources.json` に元バイトのSHA-256と行数を記録し、既存のスナップショットを上書きしない。以降、`sources/` と `sources.json` を固定する。入力を追加・変更する場合は新しいPACK（例: `LegacyApp-r2`）を作る。

## 2. 全文を読んで分割を計画する

[plan.jsonの形式と例](references/plan-format.md) を読み、`PACK/plan.json` を作る。全原文を確認し、行数は `sources.json` と照合する。

- 長い入力は行番号付きで範囲を区切って読む。ツール出力で省略された範囲を読了扱いにせず、ファイルごとに計画を保存してから次へ進む。
- 各入力行を、空行も含めて**ちょうど1回**割り当てる。省略・重複割り当て・重複内容の削除をしない。説明、例、注意書きも残す。
- 段落、コードフェンス、表、見出しによる適用条件、条件と例外を途中で切らない。順序に意味がある記述・定義と依存する記述は一緒に保持する。独立させられない場合は大きい範囲のまま残す。
- 全体に適用する義務・禁止・優先順位と、適用場面が曖昧なルールは `Agent.md` に残す。必須本文を短くするためだけに詳細へ移さない。
- 詳細は目的別に分け、`description` に「DBアクセスを移行/修正するとき」のような具体的な読む場面を書く。説明は索引であり、原文の代用品ではない。
- 矛盾は両方の原文を保持し、勝手に片方を削除・統合したり優先順位を決めたりしない。同じ設定値・対象・条件に違う指示がないか、ファイルをまたいで照合する。未解決事項と出典範囲を報告し、TOML反映を保留する。元から矛盾していたことや原文を残したことを、有効化してよい根拠にしない。

## 3. 生成・機械検証・意味レビューを行う

```text
python tools/rule_pack.py build rule-workspace/LegacyApp
python tools/rule_pack.py verify rule-workspace/LegacyApp
```

`build PACK` は全行の割り当てを検証し、原文の範囲を改行（CRLFを含む）・空白を保ったUTF-8でコピーする。見出し・出典・詳細の参照案内を追加し、`generated/Agent.md`、`generated/details/*.md`、`generated/coverage.json`、`generated/rules.toml` を生成する。検証失敗時は何も生成しない。既存の `generated/` があれば拒否する。成功後の変更は新しいPACKで行い、成果物の手修正や削除による再生成はしない。

`verify PACK` は原文の変更・追加・欠落を固定マニフェストと照合し、計画から対応表・TOML断片も含む**全出力**を再計算して比較する。出力の改変、欠落、余分なファイル、シンボリックリンクも検出する。成功を実測し、`coverage.json` で全入力の対応先を確認する。失敗したまま新ルールを有効化しない。

機械検証だけでは意味の保持は証明できない。原文と生成物を照合し、次をレビューしてから設定へ進む。

- 適用範囲・条件・例外が同じ意味で読め、必須義務が詳細の未読により失われないか。
- 並べ替えで優先順位が変わらず、矛盾や未解決事項が隠れていないか。適用判断を妨げる未解決事項があれば、有効化を止めて具体的に報告する。
- 段落・コードフェンスが閉じ、分割や追加見出しで構造が壊れていないか。
- 相対リンクが参照先に届くか。原文リンクを書き換えて検証をすり抜けず、登録済み資料との対応を確認する。参照できないリンクは未解決として報告する。
- **起動時に提供された本文と、まだ本文を読んでいない索引を区別する。** `Mandatory text` と `Applicable details` は原文であり、確認済みの記録のためだけに同じファイルを開き直させない。索引だけの資料は `Detail and example references` の `source` → `file` で保存済みRunの本文を読む。登録ファイルは `.migration-materials/rule-NNNN.txt` に改名されるため、PACKの相対リンクをRunで直接辿らせない。提供方法の整理で、適用条件・例外や編集後の確認を省かない。
- 生成した案内では、参照資料・付属ヘルパーを読み取り専用として扱い、独自の抽出・照合処理や中間データは `.migration-scratch/` に置く。資料の書き換えで検証を通させない。

## 4. 設定を案内する／依頼済みなら反映する

分割した場合の `generated/rules.toml` は絶対パスの**設定断片**であり、完全な設定ファイルではない。`Agent.md` は `required`、詳細は読む場面の `description` を伴う `reference` として `[[project.migration_rules]]` に登録する。既存ファイルの分類だけを変える場合は、該当登録の `usage` と `description` だけを編集する。`[[project.references]]` の参考実装とは区別する。

案内だけなら、対象の旧登録と置換する新登録を示す。ダッシュボードでは **プロジェクト共通の移行ルール** に絶対パスを入力し、Agentを **毎回適用する必須事項**、詳細を **必要時に読む詳細・例** にして **読む場面・内容** を入力する。

- **登録済みルールの見直し**: [確認と反映の手順](references/loading-policy.md#4-反映し設定と本文を照合する) の `rule_review.py apply` を使う。`start` が作った `config.before.toml` と `loading-before.json` を再利用し、バックアップや変更前の棚卸しをもう一度作らない。分割が必要だった場合も、この経路を使う。
- **まだ登録していない原文から新規登録する場合だけ**: [新規登録の手順](references/register-new.md) を読み、対象を照合してバックアップ後に反映する。

新設定は次に準備するRunから適用され、保存済みRunの資料は変わらない。PACKは登録後も同じ場所に保持する。報告にはPACK、生成ファイル、機械検証と意味レビューの結果、未解決事項、設定を案内したか反映したかを含める。未実行の確認は成功扱いにしない。
