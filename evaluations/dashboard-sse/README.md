# ダッシュボードのSSE描画計測

Windowsに既にあるNode.js 22以降とChrome（またはEdge）、MoCAの既存Python環境だけを使用します。5 Runの状態更新を合成データで生成し、本体のHTTP・SSE・画面を通します。PHP、移行した業務コード、Junie、業務DBは実行しません。合成Runを本物の移行ワーカーとしては起動せず、工程やキャッシュの性能は測りません。

```powershell
$env:PYTHONPATH = (Resolve-Path .\src)
python -B evaluations/dashboard-sse/benchmark.py
```

ベースラインと候補のどちらも同じ計測コードを使います。ベースラインの別worktreeを用意し、その `src` を `PYTHONPATH` に指定します。Chromeのプロファイルは毎回一時作成します。Chromeの場所が異なる場合やEdgeを使う場合は `--chrome <実行ファイルの絶対パス>` を指定してください。

最初に5 Runに各64件のSSEを流し、実行一覧集計のDOM更新回数、送信から表示状態が追いつくまで、Chromiumのタスク・スクリプト時間、レイアウト回数、JavaScriptヒープの観測値を記録します。次のRunへ切り替えて編集欄に下書きと選択を作り、サーバー側からSSE接続を切断します。同じRunに流した追加20件を `Last-Event-ID` で欠落・重複なく受け取ること、選択や未保存内容・選択範囲が維持されることを確認します。HTTP要求数、SSEフレームの本文バイト数・件数、最終表示の照合用ハッシュも出力します。ヒープはピーク値ではなく、タスク時間はPC全体のCPU時間ではありません。SSEバイト数はHTTPヘッダーを含みません。

## 計測結果

Windows実機、Python 3.13.17、Node.js 24.15.0、同じChromeで、変更前 `9107403` → 候補 → 候補 → 変更前の順に各2回計測しました。初回起動やSDKコンパイルを混ぜないよう、計測内のJunieモデル一覧とRoslynの診断処理はサンプル応答に固定しています。SSEと編集本文のHTTP、Monacoへの反映は本体を使います。

| 指標 | 変更前 2回 | 候補 2回 |
| --- | ---: | ---: |
| 選択中の64件で実行一覧の集計を書き換えた回数 | 64 / 64 | 0 / 0 |
| Chromiumのスクリプト時間 | 69.6 / 72.4 ms | 41.3 / 40.1 ms |
| 同区間のChromiumタスク時間 | 268.4 / 242.2 ms | 222.7 / 270.9 ms |
| 64件を表示し終えるまで | 292.5 / 271.8 ms | 258.6 / 281.5 ms |
| Run切り替えから最初のエディタ内容表示まで | 1.48 / 1.55 s | 5.00 / 1.24 s |
| 同区間のレイアウト回数 | 133 / 78 | 77 / 78 |
| 計測区間直後のJavaScriptヒープ | 1.60 / 1.61 MB | 1.90 / 1.90 MB |
| 全シナリオのSSE受信件数 | 150 / 150 | 150 / 150 |
| SSE接続数 / SSE受信バイト数 | 各3接続 / 167,368・167,363 B | 各3接続 / 167,365・167,367 B |
| 一覧取得 / エディタ取得回数 | 5・5 / 7・7 | 7・5 / 6・6 |

SSEフレーム数と表示・下書きの照合結果は4回とも同じです。フレーム長には時刻の桁数による差があり、定期ポーリングの回数は操作にかかった時間でも変わります。確認できた改善は、同じRunを選択し直していたための一覧さしかえの削減と、その区間のスクリプト時間です。PC全体、ネットワーク使用量、ヒープ、起動・Run切り替え時間の改善は確認していません。実Junie・5件分の実移行負荷での計測ではありません。

変更は選択Runが変わらないときの一覧の再描画の抑止だけです。接続状態が戻ったときの操作の有効化は、一覧の再描画ではなく接続状態の変化によって更新します。実行一覧の定期取得、SSEの配信・保持件数・順序、ログを追加する処理は変更していません。

## 再接続で履歴保持数を超える場合

```powershell
$env:PYTHONPATH = (Resolve-Path .\src)
python -B evaluations/dashboard-sse/history_window.py
```

実Chromium、通常のSSE受信・HTTP停止経路・Monacoを使い、合成Runの切断中に20件、100件、137件の状態更新を入れる。Windows 11 10.0.22000 / Python 3.13.17、共存候補 `fde4fac`、試験コード `f18d42f` で18.25秒。各復帰はそれぞれ3.08、3.11、3.14秒で、ブラウザーの再接続待ちも含む。速度の比較ではない。

| 切断中の更新 | Last-Event-ID | 受け取った連番 | 復帰後の状態 |
| ---: | ---: | --- | --- |
| 20 | 3 | 4–23（20件すべて） | 同じRunの停止待ち。停止操作は無効 |
| 100 | 23 | 24–123（100件すべて） | 同じRunの停止待ち。停止操作は無効 |
| 137 | 123 | 161–260（保持した最新100件） | 最新操作に追従。新しい操作の停止は可能 |

保持範囲内の連番に重複や欠落はなく、範囲を超えた古い37件は再送されない。この試験では表示は最新状態に追従したが、ログ全履歴を保証しない。停止を再送せず、次の操作への停止は1回だけ受理され、別Runには波及しなかった。通信再接続ではMonacoの未保存本文と選択範囲を維持。実際に別Runを開いて戻った場合は未保存本文を維持したが、選択範囲は同じではなかった。
