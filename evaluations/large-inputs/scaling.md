# カプセル準備・累積原文・ルール整理ヘルパーの計測

ベースは `89cfb15`。Linux / Python 3.12.14、同じ合成データを使い、ウォームアップ1回を除いた中央値。モデル待ち、実アプリ、ビルド、PHP/C#の実行は含まない。WindowsはCIの回帰確認と分けて扱う。

| 操作 | 変更前 | 変更後 | 比較条件 |
| --- | ---: | ---: | --- |
| カプセルの準備 | 485.11 ms | 253.55 ms | 3行の短いPHP関数10,000件、50万文字上限、5回。2カプセルの本文SHA-256が両方一致 |
| 累積照合と対象外ファイルの開始前/終了後照合 | 3,809.34 ms | 3,073.88 ms | 500,000バイトの原文64区間を先頭から順に供給、3回。前後のファイル一覧とハッシュが一致することを確認 |
| ルール本文2ページを再表示 | 39.49 ms | 6.24 ms | UTF-8の80行ファイル200個、計600ページ、5回。Pythonプロセスの起動時間は含まない |

累積照合は、すでに検査した展開先のハッシュを同じカプセルの起動前照合で使う。元の保存原文の照合と、Junie終了後の対象外変更検出は維持する。64区間で起動前の再読込が2,080ファイル分（論理1.04 GB）減る。過去区間すべての照合がなくなるわけではない。

ルールの再表示では、もとのルールファイルの読込が400回（2,912,000 B）から0回。固定ページは2ページ分読み込む。最初の索引出力はこのテスト環境のパス名で27,892 Bから491 B。開始時に固定ページを保存するため、その書込コストが追加される。最終確認と反映時は現在の原文を再照合する。モデルによる確認・記録の回数を削った結果ではない。

明示した701行に短い関数100個を置き、その後ろだけに4 MiBのコメントを追加する回帰ケースでは、元の701行と同じカプセル本文で、関数の途中分割なしを確認した。ファイル全体を解析する機能ではなく、指定終了行が先頭4 MiBを越える、または安全に解析できない場合は従来の分割へ戻る。

境界、行リスト、ハッシュ再利用と終了後の改変検知、原文を変更した場合の反映前検出は `tests/test_large_input_scaling.py` と `tests/test_rule_review.py` で確認する。
