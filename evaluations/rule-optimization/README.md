# ルール整理スキルの実Junie検証

2026-11-17の大量ルール・2万行PHPでの追加比較は [スキル改善の実測](large-rules.md) を参照。以下は最初の小規模ケースの記録。

2026-11-16、macOS、Junie 26.11.1（4020.10、Junie Lite）で実施。スキルによる整理・設定更新を検証した。PHP移行そのものの速度比較は [ルール読み込みの比較](../rule-loading/README.md) を参照。

## 固定ケース

```text
python evaluations/rule-optimization/create_fixture.py
python evaluations/rule-optimization/create_fixture.py --conflict
python evaluations/rule-optimization/create_fixture.py --loading
```

ハーネスをインストールしたPythonを実行できる環境で、表示された一時フォルダの `harness/` をJunieで開く。初回はプロジェクトを信頼し、`/skills` で対象スキルが有効か確認する。原文整理のケースでは以下をJunieの入力欄に送る。

```text
/harness-optimize-rules rule-workspace/LegacyApp/sources に置いたまとまっていないルールを、情報を欠落させず入口のAgent.mdと用途別の詳細Markdownに整理し、harness.local.tomlの該当する旧ルール登録を置き換えてください。原文のコピー元は ../app/docs/mixed.md と ../app/docs/views.txt です。対象外の設定は維持してください。移行はまだ実行せず、ルールと設定だけを検証してください。完了時は skill-check.done に実施内容と未解決事項を記録してください。
```

## 確認結果

| ケース | 確認内容 |
| --- | --- |
| 通常・21行 | 全行をAgent、DB詳細、画面詳細に配置。全体の義務G01〜G03はAgentに残り、重複G01も2回保持。DBの例外・SQLの数値と文字列・Razorの例外を保持。 |
| 矛盾あり・24行 | 30秒と60秒のDBタイムアウト指定を両方保持し、矛盾を報告。既存TOMLはバイト単位で変更なし。 |

通常ケースでは、旧2登録をAgentの `required` と詳細2件の `reference` に置換した。対象外のルール、コメント、スクリプト、独自セクション、移行単位は保持し、設定をバックアップして `load_config` で検証した。両ケースで準備・移行フックは実行されていない。

Junieの自己申告だけでなく、外から `rule_pack.py verify`、元ファイルとのバイト比較、全行の対応表、生成物中の規約・例外・コード例、TOMLの差分を確認した。途中で手動の修正指示は追加していない。

初期試験では矛盾を記録しながらTOMLを更新したため、「原文の保持」と「矛盾の解消」を区別する手順を補強した。別の試行ではスキルを読まずに作業したため、明示的な呼び出しで再検証し、スキル本文の読み込みもログで確認した。自然言語で名前を挙げるだけの試行は成功扱いにしていない。

通常ケースの再試験では設定バックアップの省略も見つかった。バックアップ作成とバイト一致確認を実行できるコマンドにし、編集後もバックアップと比較する手順に変更した。

ローカル回帰テストは197件、失敗なし（環境条件で2件スキップ）。全行欠落・重複、原文や出力の改変、読めないフォルダ、Windows予約名、BOM/CRLF、TOML文字列、ハーネスへの必須/詳細登録を含む。

## 既存設定の読み込み方の最適化

`--loading` の整理済みファイルと、引数なしの混在ファイルで、次の依頼を実Junieの入力欄から実行した。

```text
/harness-optimize-rules harness.local.toml のプロジェクト共通の移行ルールの読み込み方を最適化して、設定へ反映してください。作業領域は rule-workspace/LegacyApp です。必須事項を残し、必要時に読む詳細には読む場面を設定してください。原文と対象外の設定は保持し、移行は実行しないでください。完了したら作業領域の loading-review.md に変更内容と判断理由、必須本文の文字数の前後を記録してください。
```

| ケース | 確認内容 |
| --- | --- |
| 整理済みファイル | 原文・パスを変更せず、読み込み方と読む場面だけ更新。誤ってreferenceだった全体の義務をrequiredへ戻し、DB詳細と旧`units.inputs`の重複登録をreferenceに統一。Razorの説明を具体化し、適用範囲の曖昧な規約はrequiredで保持。 |
| 必須と詳細の混在・21行 | 全行を保持してAgent・DB詳細・Razor詳細へ分割。G01〜G03と元からある重複G01を保持。変更しない既存ルールをAgentへ重ねて入れず、対象外の登録・コメントも保持。 |

整理済みケースでは、`rule_usage.py` が実効設定から計測した必須本文が **1,181文字 → 93文字** となった。詳細の本文は削除されず、該当する処理の移行・修正で読む設定になっている。小さい混在ケースでは出典・索引を加えるため、必須本文は **433文字 → 721文字** に増えた。分割による短縮を常に保証するものではない。

外から原文のSHA-256、設定バックアップとの一致、対象外TOMLの保持、`rule_pack.py verify`、`load_config`を照合した。実際の指示文を生成する `write_rule_files` / `render_guidelines` でも、必須事項の保持、詳細が索引として渡ること、参照先の存在を確認した。準備・移行・フックは起動していない。途中の修正指示は与えていない。

初期試験で、編集前の必須文字数の誤集計と、変更しないルールまでAgentへ複製する挙動が見つかった。文字数は実効設定を読むツールで前後を保存し、全登録の棚卸しと分割対象の選択を分ける手順にした。説明例から原文にない話題を転用する問題と、報告表で分割元を取り違える問題にも、本文照合と`coverage.json`に基づく報告を明示した。

`--prompt`にスラッシュコマンドを渡すだけではスキルが読まれない試行があったため、対話画面から実行し、`agent_skill_read_doc`でスキルと`loading-policy.md`が読まれたことをログで確認した。

追加後のローカル回帰テストは **201件、失敗なし（環境条件で2件スキップ）**。実効設定の集計、旧登録の重複、UTF-8 BOM・CRLF・EUC-JP、報告の上書き防止と読めない資料での失敗も確認した。

これは小さい固定ケースでの挙動確認であり、意味上の分類や矛盾検出を完全に保証するものではない。全行の機械照合に加え、適用条件・例外・優先順位のレビューを行う。大量ルールの整理時間やトークン削減率は今回測定していない。

## 未調整ケースで再評価する

`holdout.py` でコピーごとに独立した合成ケースを作り、モデルには採点用コードを見せない。たとえば以下を実行する（ハーネス導入済みPythonを使用）。

```console
python evaluations/rule-optimization/holdout.py prepare C:\Temp\rule-opt-trial-01 --scenario conditional
python evaluations/rule-optimization/holdout.py score C:\Temp\rule-opt-trial-01 --scenario conditional --transcript C:\Temp\trial-01.log --signals C:\Temp\trial-01-usage.json
```

作成先でJunieを新規起動し、`/skills` を確認した上で、`/harness-optimize-rules` に「固定原文と既存登録を照合し、根拠が揃う場合だけ候補を反映してください。矛盾時は反映せず理由を記録し、準備・移行・フックは実行しないでください」と依頼する。各版・各ケースにつき同じモデル・推論条件かつ別の新規パスで最低3回実行する。候補・ログを調整に使った場合は、そのケースを未調整扱いにしない。

`artifact_outcome` はファイルだけを採点した結果で、モデルの試行結果ではない。`--transcript` にはこの作業先・1試行だけのJunieログを指定する。対象Skillによるタスクの開始、両方の資料の読込、正常終了が同じ試行で確認できなければ、`outcome` は `unverified_trial` となる。ログ形式を認識できない場合も推測で合格にしない。

開発用の静的回帰では、元のファイルが変わらないことだけでなく、登録した生成物の固定資料に元の各行が同じ回数残ることも検査します。同じ行が88回ある固定ケースで1回だけ欠落・追加しても誤反映と数えます。全行が残っていても、例外を無関係な資料へ移してCSV選択時に読めなくなれば誤反映です。移行・修正・人による除外に相当する指示の生成では、必須資料を保持し、指定した場合に限り条件・例外・優先順を併せて供給することを確認します。

```console
python -m unittest discover -s tests -p "test_rule_holdout.py" -v
```

これは固定ケースの照合であり、任意の文書の意味を判定したり、未記録の矛盾を発見したりするものではありません。既存の過去実測はその時点の評価結果です。この追加検査では実Junieを実行していません。

矛盾ケースでは、評価者が最終回答と原文を突き合わせ、保留理由が妥当な場合にその抜粋を `--signals` の `reviewed_hold_reason` に入れる。抜粋には両方の根拠行（`export.md:92` と `export-rehearsal.md:2`）を含める。実際に提出された回答の抜粋と照合できない間は `hold_reason_needs_review` とし、正常終了だけで妥当な保留に数えない。抜粋やログ本文は結果に含めない。

2026-11-23のWindows実機・実Junie（GPT-6 Luna、XHigh）で完了した既存の合成2試行を、同じ成果物・ログで再採点した。時間はタスク開始から正常終了までで、確認待ちも含む。入力はログの非キャッシュ・キャッシュ読込・キャッシュ作成を分けたもので、料金ではない。

`conditional` はページ末尾の必須事項・紛らわしい参考資料・CSVの条件／例外／明記された優先順。採点は実際のガイドライン生成で、未選択・CSV選択を別々に比較する。`conflict` は別ファイルの矛盾がある版で、元TOMLが変わらないことを確認する。出力は正しい反映・誤反映・妥当な保留・不要な保留と、スキル読込の観測値を分ける。ログ未提供・読込未確認はモデル試行の成功に数えない。ログは実際のセッションのものを使い、保留理由の正しさはレビュー記録で別途確認する。`--signals` の `elapsed_seconds`、`input_tokens`、`cached_input_tokens` は実測値が得られた場合にだけ指定する。この採点CLI自体はモデルを起動せず、精度向上を証明しない。
