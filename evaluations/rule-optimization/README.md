# ルール整理スキルの実Junie検証

2026-11-16、macOS、Junie 26.11.1（4020.10、Junie Lite）で実施。スキルによる整理・設定更新を検証した。PHP移行そのものの速度比較は [ルール読み込みの比較](../rule-loading/README.md) を参照。

## 固定ケース

```text
python evaluations/rule-optimization/create_fixture.py
python evaluations/rule-optimization/create_fixture.py --conflict
```

それぞれ表示された一時フォルダの `harness/` でJunieを起動する。初回はプロジェクトを信頼し、`/skills` で対象スキルが有効か確認する。以下をJunieの入力欄に送る。

```text
/harness-optimize-rules rule-workspace/LegacyApp/sources に置いたまとまっていないルールを、情報を欠落させず入口のAgent.mdと用途別の詳細Markdownに整理し、harness.local.tomlの該当する旧ルール登録を置き換えてください。原文のコピー元は ../app/docs/mixed.md と ../app/docs/views.txt です。対象外の設定は維持してください。移行はまだ実行せず、ルールと設定だけを検証してください。完了時は skill-check.done に実施内容と未解決事項を記録してください。
```

## 確認結果

| ケース | 確認内容 |
| --- | --- |
| 通常・21行 | 全行をAgent、DB詳細、画面詳細に配置。全体の義務G01〜G03はAgentに残り、重複G01も2回保持。DBの例外・SQLの数値と文字列・Razorの例外を保持。 |
| 矛盾あり・24行 | 30秒と60秒のDBタイムアウト指定を両方保持し、矛盾を報告。既存TOMLはバイト単位で変更なし。 |

通常ケースでは、旧2登録をAgentの `required` と詳細2件の `reference` に置換した。対象外のルール、コメント、スクリプト、独自セクション、移行単位は保持し、設定をバックアップして `load_config` で検証した。両ケースで準備・移行フックは実行されていない。

Junieの自己申告だけでなく、外から `rule_pack.py verify`、元ファイルとのバイト比較、全行の対応表、生成物中の規約・例外・コード例、TOMLの差分を確認した。途中で手動の修正指示は追加していない。

初期試験では矛盾を記録しながらTOMLを更新したため、「原文の保持」と「矛盾の解消」を区別する手順を補強した。別の試行ではスキルを読まずに作業したため、明示的な呼び出しで再検証し、スキル本文の読み込みもログで確認した。自然言語で名前を挙げるだけの試行は成功扱いにしていない。

通常ケースの再試験では設定バックアップの省略も見つかった。バックアップ作成とバイト一致確認を実行できるコマンドにし、編集後もバックアップと比較する手順に変更した。

ローカル回帰テストは197件、失敗なし（環境条件で2件スキップ）。全行欠落・重複、原文や出力の改変、読めないフォルダ、Windows予約名、BOM/CRLF、TOML文字列、ハーネスへの必須/詳細登録を含む。

これは小さい固定ケースでの挙動確認であり、意味上の分類や矛盾検出を完全に保証するものではない。全行の機械照合に加え、適用条件・例外・優先順位のレビューを行う。大量ルールの整理時間やトークン削減率は今回測定していない。
