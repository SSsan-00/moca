# 導入手順とharness-setupスキルの検証

2026-11-16に、[Windowsユーザーマニュアル](../../docs/windows-user-guide.md)、[README](../../README.md)、[harness-setup](../../.junie/skills/harness-setup/SKILL.md) を、初回導入と既存環境の相談で検証した。

## 検証方法

実機はmacOS。Python 3.13の新しい仮想環境、Git、本番のダッシュボード、Chromeを使用した。Windowsの操作案内は、実際のJunie CLI `26.11.1 (4020.10)` に仮想Windows環境の診断結果を渡して確認した。モデルは各試行で報告された `Qwen/Qwen3.6-27B-FP8`。

Junieの試行ごとにスキル・参照資料・合成したアプリ資料を別フォルダへコピーし、新しいセッションで実行した。同名の別スキルやMCP設定が混ざらないよう、試験コピーだけをスキルの読み込み先に指定した。指示は「配置資料を読む」「仮想Windows利用者への案内だけ」「インストール・編集・ログイン・移行などは実行しない」とした。正解や疑わしい箇所はユーザープロンプトへ追加していない。

スキルの読み込みと参照ファイルの閲覧はJunieのイベントログで確認した。CLIの終了コードが0でも回答が空の試行は成功扱いにしていない。

## 本番ダッシュボードでの確認

空白と日本語を含むパスにハーネスと合成アプリのリポジトリを作り、マニュアルのPython操作をmacOS相当の実行ファイル名で行った。

| 操作 | 結果 |
| --- | --- |
| 新しい仮想環境に `pip install -e .`、CLIの `--help` | 成功。仮想環境のactivateは不要 |
| 設定ファイルなしでダッシュボードを起動 | 初回の設定フォームを表示 |
| Razorの移行先を片方だけ指定して保存 | 不足する相方を表示し、不完全な設定は書き込まない |
| 空白・日本語入りのアプリと保存先をフォームに入力 | 引用符なしで保存成功 |
| 存在しないPHPを指定して準備 | エラーを表示し、worktreeを作らない |
| PHPのパスを修正して準備 | Run ID、1カプセル、manifest、worktreeを作成 |
| ブラウザーを再読み込みして保存済みRunを開く | 同じRun IDで進捗を表示 |

準備試験のサーバーはJunieと.NETのないPATHで起動した。準備後のRunにビルド結果・トークン使用量・Junie作業フォルダがないことも確認した。合成アプリ自体は、別途インストール済みSDKでビルドできた。

## Junieに渡した相談

すべて `/harness-setup` で呼び出し、同じケースの修正前後ではプロンプトとアプリ資料を固定した。入力と合成資料は [scenarios.json](scenarios.json) に保存した。

| ケース | 入力条件 | 確認する内容 |
| --- | --- | --- |
| 1. 初回導入 | Windows PowerShell。Gitあり。Pythonは3.13のみ。Junieなし、SDK一覧は空。ハーネスは取得済み。小さいPHPの移行まで案内を依頼 | Python 3.11の追加を要求しない。導入・ログイン・設定・準備を案内し、準備済みRunは「移行を再開」で続ける |
| 2. 既存設定の不足 | 空白入りアプリパス。Razorの移行先が `.cshtml` のみ。ビルド対象とチェッカーは未追跡。SDK指定は8.0.100、導入済みは10.0.201のみ。既存設定を保持して準備まで案内を依頼 | 相方を設定に追加する。新規移行先の事前作成は要求しない。SDK指定を保持する。worktreeに必要なファイルのコミットを案内する |
| 3. 既存Runの再開 | `py` なし、`python` は3.13.9。Junie・SDK導入済み。2移行単位と準備済みRunあり。Activate.ps1は実行ポリシーエラー。ファイルを変更せず、別Runを作らない案内を依頼 | activateや実行ポリシー変更を要求せず、既存Run IDの「移行を再開」を案内する |

## 発見して修正した点

- 旧マニュアルの3.11固定コマンドを受け、Junieも導入済み3.13を使わず3.11の追加を勧めた。3.11以上を使う手順に揃えた。
- 旧スキルはRazorの相方不足を見落とし、SDK不足に対して `global.json` の緩和を推奨した。先頭に設定の点検表を置いた。
- 説明を追加しただけでは、ロールフォワードの誤解や不適合なSDKの推奨が残った。SDK判断は `dotnet --version` で確認し、不足時は `sdk.version` の完全な版を使う短い参照手順にした。
- 準備済みRunの続行を「移行を実行」と案内する試行があった。新規作成と再開の操作表を設け、続行の操作名を転記する指示にした。
- 新規移行先ファイルの事前作成や、`python` に変更しても `py` 専用引数が残る案内を検出した。新規ファイルを指定できることと、ランチャー引数の扱いを明記した。
- SDK確認後にアプリフォルダから戻らずハーネスを起動する案内と、未実行の設定保存を確認済みとする回答があった。作業場所と、資料の確認・実行結果・次の操作を区別する指示を加えた。
- PHP原文の未コミット変更を読むためにもcommitが必要、という誤案内が残った。PHP原文・参照資料と、worktree内のビルド用ファイルで必要条件が異なることを明記した。
- READMEの導入経路をフォーム中心に統一した。インストールで生成される `.egg-info` はGitの対象外にした。

## 改善後の案内を確認した結果

| 相談 | 確認できたこと | 残る注意点 |
| --- | --- | --- |
| 初回導入（同じ版で独立した2セッション） | 両方で既存Python 3.13、Junieの導入・ログイン、フォーム設定、準備したRunの「移行を再開」を案内 | 2回ともSDK参照資料を読まず、1回はアプリのSDK指定の確認も省略した。導入の全前提を点検できたとは判定しない |
| 既存設定（最終修正後の1セッション） | Razorの相方追加、新規移行先の事前作成不要、SDK未導入でも準備可能、指定SDK 8.0.100の追加、PHPは未コミットでも読めること、ビルド対象・チェッカーのcommitを案内。既存設定全体や `global.json` の上書きは勧めなかった | SDK参照資料は読んだが、回答から `dotnet --version` の実結果確認手順が抜けた。全項目合格とはしない。Windowsコマンド実行も未検証 |
| 既存Runの再開 | activate・実行ポリシー変更を要求せず、`.venv`の確認と指定済みRun IDの「移行を再開」を案内 | 案内の確認であり、Windows上での再開処理を実行したものではない |

既存設定の最終試行は約34秒で回答した。直前の試行ではSDKと作業場所の案内が改善した一方、PHP原文のcommitを必須とする誤りが残り、修正後に同じ入力で再試験した。最終回答ではその区別とハーネスの起動場所が正しく、未実行の保存・準備を確認済みとも表現しなかった。

スキルは段階的に修正したため、上表の初回導入・再開の試行と、既存設定の最終試行ではスキルの版が異なる。すべての相談を最終版で繰り返し合格させたという意味ではない。改善は確認できたが、モデルによる手順の省略があり、完全自動の環境構築を保証する評価ではない。

## SDK 9以降を再利用する方針での追試

利用者の開発環境にはSDK 9以降があるという前提を追加した。通常導入では既存SDKを使い、SDK選択が失敗した場合にだけ追加導入を検討する。SDK固定の例は例外ケースとして残した。上記の旧試行と異なり、今回は同じ最終版の資料で4ケースを実行した。

| ケース | 最終試行の結果 | 秒数 |
| --- | --- | ---: |
| SDK 9.0.203、net9.0、global.jsonなし | 既存SDKを使用。追加SDKを要求せず、アプリでの `dotnet --version` と同じRunの再開を案内 | 34.0 |
| SDK 10.0.201、net9.0、global.jsonなし | 既存SDKを使用。SDK 9への入れ直しや固定ファイル作成を要求せず、選択確認と同じRunの再開を案内 | 40.3 |
| SDK 10のみ、global.jsonで8.0.100指定 | 選択確認後、失敗時に指定SDKを追加する案内。既存の指定は保持し、フォームで設定を修正 | 40.5 |
| 保存済みRunの続行 | 同じRun IDで再開。activate、実行ポリシー変更、再インストールを要求しない | 30.4 |

最初の試行ではSDK 10の確認コマンド省略、例外ケースでのSDK指定変更の提案、再開時の不要な `pip install` があった。回答前の確認項目を加え、同じ入力で再試験した。両試行の回答と資料ハッシュは [sdk-policy-results.json](sdk-policy-results.json) に保存した。全8セッションでスキルを読むイベントを確認した。

最終試行は今回のSDK再利用・指定保持・再開の判断を満たした。ただし案内全体の完全合格とはしない。SDK 10の回答にビルド成功を強く言い切る表現があり、例外ケースではSDKが準備の必須条件ではない点の説明が薄い。SDK選択と実ビルドの成功は別であり、実行結果で確かめる。準備はSDKを使うスクリプトがなければ先に進められる。この区別はマニュアルとスキルに保持している。

## 検証範囲

Windows実機でのインストーラー、`h.cmd`、初回認証画面の操作は未検証。実案件のPHP移行精度も、この導入試験では判定していない。模擬相談の成功は、すべての環境や毎回のJunie回答が正しいことを保証するものではない。

## 再検証するには

1. 一時フォルダへ `scenarios.json` の `copy_from_repository` にある資料をコピーする。各ケースの `files` を、キーに示した相対パスへ書き出す。実際の個別設定や認証情報はコピーしない。
2. ケースごとに新しいJunieセッションを使い、試験コピーだけをスキルの読み込み先にする。`system_prompt` とケースの `prompt` をそのまま渡す。期待回答や過去の誤りはプロンプトに追加しない。
3. Junieの版・モデル、スキルと資料のハッシュ、読込イベント、回答、所要時間を保存する。資料を変更していないことも確認する。
4. 上表の判断と実際の案内を比較する。CLIが正常終了しても、空の回答や誤案内は合格にしない。失敗した試行を除外して成功率として示さない。

Windows実機で追試する場合は、マニュアル第1・2・5節に沿って、導入、フォーム保存、準備、同じRunでの移行を順に確認する。本記録の模擬相談とは区別して結果を残す。
