# PHP → C# Migration Harness

Pythonで、PHPからC#やASP.NET Core Razor Pagesへの移行を支援するローカル実行用ハーネスです。コード移行はJunieに依頼し、ハーネスが対象範囲、作業場所、実行記録を管理します。

Windowsでの導入・操作手順は [Windowsユーザーガイド](docs/windows-user-guide.md)、実行順序・保存形式・再開の条件は [技術仕様](SPEC.md) を参照してください。

## はじめる（Windows）

Python 3.11以上とGitを用意し、PowerShellで1行ずつ実行します。未導入ツールの入手先やエラー時の対応は、[ユーザーマニュアルの第1節](docs/windows-user-guide.md#1-ダッシュボードを起動する)を参照してください。

```powershell
git clone https://github.com/SSsan-00/php-to-csharp-migration-harness.git
Set-Location .\php-to-csharp-migration-harness
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\php-to-csharp-harness.exe --help
.\h.cmd d
```

`py -3 --version` で3.11以上が使えることを確認します。`py`がなく `python` が使える場合は `python -m venv .venv` に置き換えます。既にclone・インストール済みなら、そのフォルダで `.\h.cmd d` から始めます。仮想環境の有効化や設定ファイルのコピーは不要です。

端末に表示されたURL全体を開き、**設定 → プロジェクトの詳細設定** と **移行単位** を入力して保存します。まず **実行 → 準備のみ** でRun IDが作られることを確認します。移行にはログイン済みJunie CLIが必要です。.NET SDKは導入済みの9以降を再利用し、アプリ側にSDK指定がある場合はその条件を確認します。準備したRunは **実行一覧 → 再開** から続けられます。

Junieを使える場合は、ハーネスのフォルダで起動して `/harness-setup` に導入のサポートを頼めます。 [スキルの使い方](docs/windows-user-guide.md#junieに設定手順を案内させる)

## 現在の実装

- 移行単位ごとに、移行元PHPと移行先をTOMLで指定する
- 移行元を行番号付きコンテキストにまとめ、設定上限ごとのカプセルに分割する
- アプリ用のGit worktreeを、指定した基準リビジョンから作成する
- `run`では、設定した移行先ファイルと、その回のカプセルを渡し、Junie CLIを順番に起動する
- 各Junie呼び出し後に編集を許可した移行先をworktreeへ反映し、実行記録を保存する
- 全カプセルの反映後にworktreeで `dotnet build` を実行し、結果を `run.json`、出力を `build.log` に保存する
- ビルド成功後に `after_build` のスクリプトと設定済みの独自チェッカーを順に実行し、チェッカーの終了コードを `run.json`、標準出力と標準エラーを `checker.log` に保存する
- 移行先に限定できるビルドエラーや対応形式のチェッカー指摘を、設定した回数内でJunieに渡し、修正後に再検証する
- 人が指摘を問題なしと判断した場合は理由を記録し、同じRun IDで確認を続ける
- 同じRun IDで、未完了カプセルの移行またはビルドからの再検証を再開する
- Junieがモデルサービスとの通信失敗を確定した場合は最大2回再試行し、中断した自動修正を修正回数に含めず再開できる
- JunieにPHPとC#の対応行を提案させ、アンカー付きのDiff ViewerワークスペースJSONを保存する
- ダッシュボードで最大5件のRunを並列実行し、Runごとに進捗・編集・指示・停止・再開を管理する
- 設定タブでJunieのモデルと推論の強さを選び、同じRunの再開や自動修正にも引き継ぐ
- 生成・編集した移行先ソースファイルをBOM付きUTF-8で保存する

アンカーの座標は保存前に検証します。PHPとC#の意味上の対応はDiff Viewerで確認できます。`resume` は `run.json`、保存済みのカプセル、作業ツリーを使います。

Junieには移行元・移行先を静的に確認し、業務コードやDBを実行しないよう指示します。移行元が実行可能であることは前提にしません。ハーネスは設定済みのビルド・チェッカー・追加スクリプトを実行するため、実行確認が不要な案件では静的なチェッカーを指定します。[業務PHP 2,000行・資料200件の検証](evaluations/business-php/README.md)に、その構成と確認範囲を記録しています。

Junieへ渡す情報と作業フォルダはハーネスで絞りますが、別の絶対パスへのアクセスをOSレベルで遮断するものではありません。Junieを使うと、選択したコンテキストがJunieのサービスへ送られます。生成後は`run.json`とworktreeの差分を人が確認してください。

## ハーネスの回帰テスト

ハーネスのリポジトリで、Python 3.11以上とGitが利用できる環境から実行します。

```console
python -m pip install -e .
python -m unittest discover -s tests -v
```

テストは一時ディレクトリにGitリポジトリとRunを作ります。準備処理はPythonとGitで実行し、制御のテストではJunieや.NETなどをテスト用の処理に置き換えます。GitHub ActionsはmainへのpushとPRで、WindowsとLinuxのPython 3.11・3.13を検証します。

GitHubでIssueを1件ずつ処理する管理者向け手順は、[Codex Issueワークフロー](docs/codex-issue-workflow.md)を参照してください。

コードの担当範囲と主なテストは [技術仕様の「実装の入口」](SPEC.md#実装の入口) にまとめています。実行順序は `workflow.py`、移行先ファイルの読み書き・反映は `worktree_targets.py`、チェッカー出力の解析は `checker_output.py`、並列実行は `run_manager.py` が担当します。

## 設定の補足（CLI・TOML）

入力例、単位、既存 Run への反映時点は[詳細設定の選び方](docs/windows-user-guide.md#詳細設定の選び方)を参照してください。

設定タブの「移行先周辺の参照資料」で、共通の参照起点と追加フォルダーを指定できます。移行単位別の上書き、除外、再帰収集、件数・バイト数の上限は **TOMLを直接編集** で指定します。`[target_context]` が共通設定で、`[units.target_context]` は指定した項目を上書きします。`roots` の省略時は親フォルダー、`inc`、`Libs`、`Extensions` を使い、`roots = []` なら `folders` で追加したフォルダーだけから収集します。初回収集の設定と結果は `capsule/target-context/manifest.json` に固定され、同じRunは保存版を再利用します。

Junie を起動する際の指示と同梱ガイドラインの容量は、`[junie]` の `warn_input_bytes` と `max_input_bytes` で警告・停止を設定できます。起動入力と同梱したルールの量は `run.json` の `last_junie_input` に記録します。後からツールで読み込む参照資料や、モデル側の追加コンテキストはこの容量に含みません。

通常の導入と設定はダッシュボードから行えます。以下はTOMLやCLIを使う場合の補足です。`harness.local.toml` にはアプリのGitリポジトリ、基準リビジョン、保存先、移行単位を指定します。worktreeと実行データは両リポジトリの外に置き、互いに入れ子にしません。設定例は [harness.example.toml](harness.example.toml) を参照してください。

パスは絶対・相対のどちらでも指定できます。相対パスの基準と読み書きの範囲は次のとおりです。

| 設定 | 相対パスの基準・制約 |
| --- | --- |
| `project.root`、`project.worktree_root`、`project.run_root`、`diff_viewer.anchor_reference` | 設定ファイルがあるディレクトリ。 |
| `source`、移行ルール、参考実装、`units.inputs`、`diff_viewer.html`、仮C#のコピー元 | アプリルート。アプリ外の絶対パスも読み取れます。 |
| `target` / `targets`、`build.project`、仮C#のコピー先 | アプリルート。絶対パスもアプリリポジトリ内に限ります。worktree内のパスへ正規化し、元のリポジトリには書き込みません。 |

スクリプトやチェッカーの通常のコマンド引数は、実行工程の作業ディレクトリが基準です。仮C#取り込みの `@copy-migration-draft` は上表に従います。

たとえば、メニュー機能を移行する単位は次のように設定します。

```toml
[[units]]
id = "メニュー"
source = "php/menu.php"
targets = ["Pages/Menu.cshtml.cs", "Pages/Menu.cshtml"]
# 仮C#／Razorをこの移行単位の初期内容として取り込む場合に指定する。
draft_imports = ["../draft/Menu.cshtml.cs", "../draft/Menu.cshtml"]
```

`id` は設定ファイル内で一意の機能名です。`"メニュー"` や `"menu"` のように、日本語でも英数字でも指定できます。`source` にはアプリルートからの相対パス、または外部ファイルの絶対パスを指定できます。拡張子なしを含め、拡張子を問わず移行元PHPとして全文を固定し、1行目からファイル末尾までをJunieに渡します。Razorページは、同じディレクトリと名前の `.cshtml` と `.cshtml.cs` を `targets` に指定します。相方が不足している場合は、ダッシュボードの設定保存やCLIの設定読み込みがエラーになります。通常のC#ファイル1つなら `target` が使えます。同じRun IDで再開するときは、Run作成時と同じ移行先を指定します。チェッカーの指摘はファイルごとに追跡します。

`draft_imports` は移行単位ごとの任意設定です。Junieの移行前に、設定したファイルをこの移行単位の作業ツリーへコピーします。移行先が1つならそのファイルへ、複数なら大文字・小文字を区別せず拡張子が一致するファイルへ取り込みます。`.cshtml.cs` は複合拡張子として扱います。`.cs` のコピー元に対して `.cs` の移行先がなければ、`.cshtml.cs` の移行先を探します。対応する移行先が0件または複数件の場合や、複数のコピー元が同じ移行先に対応する場合は設定エラーになります。

旧設定の `[scripts].before_migration` にあるコピーコマンドは引き続きプロジェクト共通で実行されます。移行単位に限定するには、対象のコピー元を `draft_imports` に移し、対応する共通スクリプトを削除してください。

反映中に停止した場合は、内容のハッシュを照合して同じRun IDから残りを反映します。移行先や保存済みのJunie出力に外部編集があった場合は、該当ファイルを照合してから再開してください。全カプセルの反映後にビルドします。

生成する移行先ソースファイルは **BOM付きUTF-8** で保存します。Junieの移行・自動修正・追加指示の結果をworktreeへ反映するときにBOMを付与し、本文と改行は保持します。エディタやビルド失敗時の確認画面から保存する場合もBOM付きUTF-8になります。

画面で編集できるサイズは、保存後のBOMを含めて8 MiB以下です。UTF-8以外の出力は反映前に停止します。保存と中断後の復旧の詳細は [技術仕様の「移行先ファイルの保存」](SPEC.md#移行先ファイルの保存) を参照してください。

`[[units.inputs]]` では、注釈版PHPや仮C#などのファイルと開始・終了行を指定できます。参照資料として `source` に追加することも、従来どおり `[[units.inputs]]` だけで移行範囲を指定することもできます。`max_context_chars`の既定値は500,000文字です。これは1回のJunie呼び出しに渡すコンテキストカプセルごとの上限であり、トークン数の厳密な上限ではありません。固定PHPから名前付き関数・メソッドの字句上の境界を取得でき、関数全体が上限に収まる場合は、その途中で分割しません。4 MiBを超えるPHPでも、明示した終了行までが固定ファイルの先頭4 MiB内に収まれば、先頭からそこまでを静的に確認して、閉じた関数の境界を使います。範囲が読み取れない、または構文を安全に確認できない場合は分割準備のログとmanifestに理由を記録します。上限に入らない関数、未対応の構文やPHPとHTMLの混在は従来どおり行境界を使い、`run`は順番にJunieへ渡します。1行自体が上限を超える場合は文字位置を記録して分割し、隣接する断片の前後512文字（上限の小さい設定ではその5%）を読み取り用に重ねます。AIには重なり部分を再移行せず、指定されたfocus範囲だけを処理するよう指示します。文字コードを明示する場合は、`source` に対しては同じ `[[units]]` に `source_encoding`、`[[units.inputs]]` に対しては `encoding` を指定します。`auto`ではUTF-8 BOMを優先し、BOMなしの場合はUTF-8とEUC-JPを厳密に判定します。両方で異なる文字列として読める曖昧な入力や、どちらでも読めない入力は自動選択せず、`"utf-8"` や `"euc-jp"` の明示指定を求めます。対象ファイル全体や会話履歴・ツール出力は文字数に含みません。

プロジェクト共通のルールは `[[project.migration_rules]]`、参考実装は `[[project.references]]` にファイルごとに指定します。ルールと参考実装は全文をRunに保存します。既存ルールは毎回適用する必須事項として、全文をJunieの起動時の指示に渡します。

設定画面で「必要時に読む詳細・例」に分類したファイル（`usage = "reference"`）は、初回編集前にJunieが全カプセルの移行元と「読む場面・内容」（`description`）を照合します。必須方針・標準の参考実装・移行先周辺の固定資料は、必要な箇所だけを読み、保存版のファイルと行を判断根拠として記録できます。情報不足は非該当と区別し、候補を残します。該当と判断した詳細や移行先が明記された詳細の原文を渡し、そのほかの本文はRunの準備資料に保管します。索引と全カプセルの本文が24,000 UTF-8バイト以内なら、ガイドラインにまとめて渡し、Junieの最終回答をJSONとして受け取ります。上限を超えた場合は原文をファイルで参照します。詳細索引とソース一覧が64,000 UTF-8バイト以内なら、その一覧をガイドラインに載せます。原文をファイルで参照する場合、Junieは用意された判定ファイルに結果を記入します。どちらの場合もハーネスが全件分のID・適用可否・理由を検証してRunに保存します。修正や再開にも同じ判定を使います。分類の変更は次に準備するRunから適用されます。必須事項を大量に登録すると入力トークンは増えます。指示の適用は理解や遵守を保証するものではなく、判定可能な規約は独自チェッカーで検証します。

複数カプセルの移行では、現在の区間までの原文を `.migration-materials/source-*.md` に順番どおり保存します。共通の例や参照用の境界行を除き、Junieが累積したデータの値・順序・重複を原文と機械的に照合できるようにします。先の未処理区間は含めません。これもAIへの作業指示であり、出力の正しさはビルド・テスト・チェッカーで別途確認します。大規模入力の実測条件と結果は[2万行・資料200件の検証](evaluations/large-inputs/README.md)を参照してください。

参考実装は、Junieが目次から対応するPHPとC#／Razorを探し、関連する範囲を読みます。修正や再開にも準備時の資料を使用します。移行単位だけで使う他の参照入力は `[[units.inputs]]` に `shared = true` を指定できます。ルールと参考実装ペアの登録手順は、[Windowsユーザーマニュアル](docs/windows-user-guide.md#3-移行ルール参考実装独自チェッカーを追加する)を参照してください。ルールと参考実装はカプセル本文の文字数上限とは別に保持します。その他の共通入力と見出しの分を確保し、残りに移行対象を詰めます。共通入力だけで上限を超える場合は準備時に理由を表示します。再開時は保存済みのカプセルを使います。

原文の改行（LF、CRLF、CR）は抜粋にも保持します。生成するMarkdownの区切りはLFで、manifestの文字数は保存するUTF-8本文を文字単位で数えます。

繰り返し呼び出しや長い定数表では、PHPから値と順序を機械的に抽出し、文字列のエスケープを解釈して移行先と照合するようJunieへ指示します。配列の区切りやカプセルの接続部分も検証し、ルールで指定されたヘルパー・共通定数の参照は、同じ結果になるリテラルで置き換えません。不一致の自動修正にも保存済みカプセルと同じルールを使います。

引用符付きの固定文字列には、Junieの作業領域へ配置する抽出補助を使います。カプセルの指定行範囲を検査し、参照用の隣接行を混ぜません。不完全な代入、変数展開を含む文字列、文字コードの確認が必要なバイト表現は推測せず、原文の確認を促します。この補助はPHP全体を解釈するパーサーではありません。抽出用の一時ファイルは専用の `.migration-scratch/` だけで扱い、アプリには移行先ファイルだけを反映します。

同じ14ルールと2万行PHPを使った初回精度・所要時間・トークンの比較は[大量ルールの検証記録](evaluations/rule-loading/large-php.md)を参照してください。失敗した中間試行も含めています。

### 大規模ソースの情報欠落を防ぐ設計

移行対象を文字数上限に合わせて分割し、`run`で順番にJunieへ渡します。`capsule/manifest.json`に各カプセルの文字数、文字コード、元ファイル・行範囲、行内のfocus範囲と重なり範囲を記録します。巨大な1行では前後の文字列を重ねて渡し、Junieが境界付近の文脈を参照できるようにします。同じ入力のカプセル間では前後最大12行ずつを文字数を制限した読み取り用抜粋として渡します。Junieは移行先にある前回までの編集と照合し、今回の担当範囲を処理します。複数カプセルになった場合は、`run.json`の確認フラグに従って分割位置をレビューしてください。

ダッシュボードの **移行台帳** では、Run IDごとに、カプセルに含まれるPHPの行範囲、設定した移行先ファイル、処理状態を確認できます。範囲は `capsule/manifest.json`、完了数と処理中のカプセルは `run.json` に保存され、同じRun IDで再開した後も確認できます。**処理済み** はJunieの完了記録が反映された状態です。処理の対応関係はDiff Viewerでレビューします。

準備時に参照PHPの原文をRun配下の `capsule/php-sources/` に保存します。Diff Viewerとアンカー生成は、このコピーをmanifestの文字コードとSHA-256で照合して使います。この仕組みを導入する前のRunでは、manifestのパスと文字コードで現在のプロジェクトから読みます。移行時点の原文を確認するには、元の版でRunを作り直してください。

ダッシュボード上部の **比較ツールを開く** メニューから **Junieで対応行を提案して開く** を選ぶと、ハーネスが処理済みのPHP範囲に対応する候補をアンカーから割り出し、同じRun IDの `run.json` に自動で保存します。候補のファイルと行範囲を確認し、**候補をDiff Viewerで開く** から元のスナップショットを見直せます。

候補を絞れない範囲は **要確認**、候補の保存後に移行先が変わった範囲は **要再確認** と表示します。以前に記録した対応は、移行先の内容が一致していれば **人の確認済み** と表示します。進捗デモでも、同じ操作で模擬データを確認できます。

入力設定に `symbol = "get_status_label"` を指定すると、台帳に元のシンボル名を表示します。移行台帳では記録済みの判断と理由を確認でき、**差分を開く** で移行先を見直せます。

CLIを使う場合は、台帳に表示した範囲IDを指定します。

```powershell
.\.venv\Scripts\php-to-csharp-harness.exe ledger-review --config harness.local.toml --run-id RUN_ID --range 1:1 --range 2:1 --state excluded --reason "旧画面でのみ使用"
```

`--state` は `confirmed`（確認済み）、`excluded`（理由付きの対象外）、`needs_review`（要確認）から選びます。現在の対応候補を確認した場合はそのまま `confirmed` にできます。候補を作れない範囲や複数ファイルにまたがる範囲では、Diff Viewerで確認した移行先を `--target` で指定します。複数の範囲をまとめて指定すると、同じ移行先で確認を記録します。

```powershell
.\.venv\Scripts\php-to-csharp-harness.exe ledger-review --config harness.local.toml --run-id RUN_ID --range 1:1 --state confirmed --target Pages/Menu.cshtml.cs --target Pages/Menu.cshtml --reason "原文と画面・PageModelの対応を確認"
```

**移行完了** になるのは、台帳の全PHP範囲が確認済みか理由付きの対象外になり、現在の入力に対してビルド、設定済みの検証スクリプト、チェッカーが成功しているときです。チェッカーの指摘を理由付きで承認し、再実行でも承認済みの指摘だけが残った場合も条件を満たします。確認した移行先が変わった範囲は、理由を残して **要再確認** に戻ります。対象外の判断は保持します。

手修正にはダッシュボードのエディタを使います。台帳は移行先の版、ビルド先・検証コマンドに加え、特定できるチェッカーと検証前後スクリプトのファイルを照合します。期待値ファイルは `[checker].verification_files` に指定できます。照合したファイルが変わると **前回合格・要再検証** と表示します。自動で特定できない依存ソースやプロジェクト設定が変わった場合も **ビルド・チェックを再実行** を選んでください。

チェッカー単独再開に対応する構成では、ビルド前後に作業ツリー、.NET 起動ファイル、SDK 参照パックを照合し、成果物の版を保存します。チェッカー単独再開とその結果を台帳に表示するときにも再照合します。対象が大きいほど読み取りに時間がかかり、停止時は OS の列挙・読み取りが応答するまで待つ場合があります。対象構成と [再開方法の一覧](docs/windows-user-guide.md#再開方法を選ぶ) を参照してください。

Diff Viewerでもworktreeの移行先は1回だけ読み、必要な版情報はその読み取り内容から作ります。ハーネスによるファイル置換・工程変更は取得前後に確認し、並行して更新され得るJunieの下書きと旧Runの外部PHPは内容の再照合を続けます。

移行先が変わったら、差分を確認してCLIで判断を登録します。再検証はダッシュボードの **ビルド・チェックを再実行** を選ぶか、同じRun IDで `resume` を実行します。検証記録のない旧Runも、同じ操作で再検証できます。

固定PHPの目録と行範囲を、作業コピーを読み直さずに参照できます。

```powershell
python -m migration_harness.cli context-evidence --config harness.local.toml --run-id RUN_ID
python -m migration_harness.cli context-evidence --config harness.local.toml --run-id RUN_ID --source-id php-0001 --start-line 10 --end-line 20 --max-chars 1000
```

`next_offset` があれば、同じ取得条件に `--offset` を足して続きを読みます。指定範囲は保存時の入力範囲に限り、文字コードと原本のハッシュを照合します。`--through-capsule N` を付けると、第Nカプセルより後の担当範囲は取得できません。未処理部分を含む分割行は全行の取得を拒否します。この目録が示す関数名と範囲は字句上の候補で、機能、呼び出し先、適用ルールやレビュー結果を確定するものではありません。このPHP目録だけでは関連資料の意味上の対応は検証できません。

設定済みの入力シンボルやPHPの名前付き関数を調べるには、`context-evidence --config harness.local.toml --run-id RUN_ID --feature NAME` を実行します。指定名に一致する固定原文の範囲と資料IDを表示します。設定者が指定したシンボルと、構文から拾った関数名は別々に表示します。同名の結果は統合せず、業務上の同一性・呼び出し先・移行先との対応は保証しません。未分類の原文も従来どおり取得できます。

`context-evidence --config harness.local.toml --run-id RUN_ID --last-plan` は、直近の移行・再開・修正で組み立てた参照計画を表示します。担当部分、過去の照合範囲、修正診断、移行先の記録された版、供給済みルールの一覧を確認できます。実際に読み取った証拠や検証合格を示すものではなく、担当原文や必須・適用ルールは計画に関係なく従来どおり渡します。計画を保存した呼び出しがまだなければ、`plan` は `null` です。

移行先の固定参考資料は `context-evidence --config harness.local.toml --run-id RUN_ID --target-references` で一覧表示できます。取得時は `--source-id target:Pages/Shared/Example.cshtml --start-line 1 --end-line 20` のようにIDと行を指定し、`next_offset` で続きを取得できます。`--related-to target:Pages/Shared/Example.cshtml` は同じ固定パスのコードビハインドを名前規約で探索します。修正時は診断に名前が出た固定資料が一意なら参照候補を `--last-plan` に表示します。同名で曖昧な候補、改変されたスナップショット、予算を超える資料は自動採用しません。 一覧は50件ずつ、本文は1ページ最大16,384文字です。参照目録と個々の取得対象には各2 MiBの上限があり、UTF-8（BOMの有無を問わない）とBOM付きUTF-16／UTF-32を厳密に読みます。この取得上限は参照資料を作業領域に固定するTOML設定とは別です。これらは参照案内であり、C#のシンボル束縛や障害原因を証明するものではありません。

未解決の確認事項は `context-handoff --config harness.local.toml --run-id RUN_ID --source-id php-0001 --start-line 10 --end-line 20 --note "例外時の戻り値を確認"` で追記できます。記録には固定PHP、現在の移行先、手動ルール採否の版を付けます。範囲引数なしで状態を一覧表示し、訂正時は `--supersedes` に以前のIDを指定します。版が合う未解決のメモだけを、関連する移行・再開・自動修正の補助情報として表示します。メモは確認済みの根拠にはなりません。

Junieも、移行カプセル・追加指示の反映・自動修正の呼び出しごとに、判断・仮説・確認待ちを計3件まで任意で残せます。内容と対象の版は保存Runの `run.json` の `junie_memos` に記録します。完了前に停止した場合は、セッション終了と対象外の変更がないことを確認できた下書きにメモを別記録として保存します。版が一致する再開だけで未確認の手がかりとして渡し、採用済みにはしません。原文範囲の照合に失敗するメモは無視し、対象やルールが変わった場合は古い本文を渡さず、確認待ちの出典だけを次回の手がかりにします。人の最新の指示を優先し、進捗・ビルド・検証結果はメモからは更新しません。


## 実行

### ダッシュボードから管理する

WindowsのPowerShellで `.\h.cmd d` を実行し、端末に表示されたローカルURLを開きます。CLIを直接呼ぶ場合は `.\.venv\Scripts\php-to-csharp-harness.exe dashboard --config harness.local.toml` を使います。

- **設定** のフォームでプロジェクト、移行単位、移行ルール、参考実装のペア、自作スクリプト、ビルド対象、独自チェッカーを編集して保存します。リポジトリと保存先、ビルド対象、共通チェッカー、基準リビジョン、Junieのモデル・推論の強さ・ステップ数上限、差分ビューアーは **プロジェクトの詳細設定** にあります。初回は設定例を表示し、内容を検証してから保存します。
- **実行** で移行単位を複数選び、**準備のみ** または **選択したN件を実行** を押します。同時実行数は **最大5件** で、残りは実行待ちに入り、枠が空くと順に開始します。同じ移行単位の実行中・待機中の重複登録は拒否します。
- **実行一覧** で状態・現在の処理・経過時間を確認し、Runごとに **進捗**・**エディタ**・**停止**・**再開**・**待機を取消** を操作します。**検証済み** はビルド・チェックの結果で、移行台帳の確認が完了したことは意味しません。
- **進捗** と **エディタ** の上部にある **表示する実行** で対象Runを切り替えます。他のRunは処理を続けます。表示対象はブラウザーごとに独立し、未保存のコードと入力途中のエディタ指示は同じページ内でRunを切り替えても保持します。未保存の内容はブラウザーの再読み込み前に保存してください。
- 実行待ちや準備中は、**実行一覧** の **Junie** から会話欄を開き、「今何してる？」と送ると現在の工程を確認できます。準備が完了すると同じ画面にエディタが表示され、照会履歴も引き続き確認できます。
- Junie の操作確認はどのタブ・Runからでも回答できます。現在のRunや編集中の内容は切り替えません。複数件あるときは1件ずつ表示し、**あとで** を押した確認はヘッダーの **Junie の確認待ち** から開けます。実行一覧の **回答待ち** も表示されます。回答待ちのプロセスも実行枠を使います。
- Windowsでは、確認待ち・自動で先へ進めない停止・設定した工程の完了を通知します。途中の自動修正や手動停止では通知せず、完了通知はダッシュボード起動中にRunごとに1回です。移行のみ・ビルドのみ・チェッカー実行済みを区別し、移行台帳の確認までは通知で完了扱いにしません。通知をクリックすると既定ブラウザーで該当Runと確認画面を開きます。Junieの確認が回答・取消済みならその旨を表示し、通知内で直接承認はできません。Windows PowerShellの登録済み通知IDを使用します。`[junie_notifications]` の `enabled = false` で無効、`repeat_after_seconds = [60, 180, 300]`（既定）で、初回から1・3・5分後に未回答のJunie確認だけを再通知します。通知リンクを開くと同じ確認の再通知は止まりますが、回答は画面で行います。等間隔を明示設定した既存の `interval_seconds`／`repeats` も引き続き使えます。工程途中の通知は既定で無効です。例えば同じ設定欄で `milestone_after_seconds = 600` を設定すると、開始から10分以上経過した移行がビルド・検証に進む際、ダッシュボードが前面になければ1回通知します。Windowsの設定や通知ホストに関わらず、画面から状態を確認できます。
- 実行待ちは `run_root/dashboard-queue.json` に保存し、ダッシュボードの再起動後に継続します。起動済みのRunを自動で再実行せず、保存された工程から **再開** します。端末で終了すると実行中のRunには停止を要求し、待機中の登録は残します。
- Junieのプロセス終了を確認できないRunでは、同じRunの会話依頼を自動実行しません。画面の案内に従ってログと残存プロセスを確認してから、新しい依頼を送ってください。別Runの処理は続行できます。
- Runごとにworktree・Junie・ログ・停止要求を分離します。共有入力を書き換える `before_prepare` から入力の保存・worktree作成までは直列に実行します。別Runの成果物は自動で合流しないため、互いに独立した移行単位を並列化してください。実行中または待機中のRunがある間は設定を保存できません。
- **進捗** で工程ごとの経過時間、実行状況、差分、移行台帳を確認できます。**Junieの累計トークン** は使用量の報告があるたびに加算し、**カプセル本文の文字数** は処理するカプセルが切り替わると変わります。実行中の **停止** で編集を保存して止め、同じRunを再開できます。Junieが操作の許可を求めると、確認ダイアログから回答できます。
- **進捗 → Junie に指示** から追加指示を登録できます。ダッシュボードで実行中のJunieが途中入力に対応していれば、移行・追加指示・自動修正の実行中にもすぐ渡します。画面には現在の送信タイミングを表示します。即時送信できない場合、移行中は作業区間の終了後に渡し、最終区間の指示もビルド前に反映します。ビルド・チェッカーの開始後に即時送信できなかった指示や、停止中に登録した指示は、同じ Run を再開したときに渡します。自動修正中に手修正を保存して追加指示を送ると、現在の修正を自動で区切り、Junieの途中の変更と手修正を合流して指示を渡し直します。対応後はハーネスが再ビルドします。競合がある場合はエディタで解消して再開します。競合がなければ手動の停止・再開は不要です。それ以外の工程で手修正が反映待ちの場合は、ファイルの合流まで指示も待機します。受信しただけでは反映済みとせず、追加指示の完了記録も確認します。未完了や即時送信の拒否時は指示を送信待ちに戻します。
- **エディタ** の **.cshtml.cs**・**.cshtml**・**.cs** ボタンから、設定済みのUTF-8・8 MiB以下の移行先ファイルを開いて編集できます。**PHP** では、移行元に登録したソースを拡張子に関係なく読み取り専用で開けます。移行中は Junie がディスクに保存した変更を表示し、編集中の下書きは **差分** で比較できます。**保存** と **↑** で登録した変更や追加指示は Run に残ります。移行先の編集は、ビルド・チェッカー・自動修正・停止処理中も保存できます。未作成の移行先も保存対象です。移行中の手修正は区間の終了後に合流し、ビルドなどの実行中に保存した編集は同じRunの再開時に反映します。自動修正中は、保存後に追加指示を送ると、その場で修正を切り替えて編集を反映できます。保存済みの編集は画面を再読み込みしても残ります。追加指示は画面に表示されたタイミングで渡します。同じ箇所を編集した場合は、エディタ上で内容を調整して **競合を解消して保存** を選び、**進捗** から再開します。保存した手修正は次の作業区間や修正時に差分として Junie に渡します。Junie には編集を原則として維持し、明らかな不具合だけ根拠を記録して修正するよう指示します。意図の確認が必要な場合は提案した変更の反映を止め、エディタに質問を表示します。回答を追加指示に登録して、進捗タブから再開できます。
- エディタ横の **Junie** には「今何してる？」「保存した版でビルドして」「チェッカーをもう一度」などを送れます。受付後に次の操作や確認質問が指示の下に表示されます。「ビルドだけ」「チェッカーまで」などの確認への回答も同じ欄から送れます。「今のビルドを止めて、保存した版でやり直して」は、実行中のビルドが止まったことを確認してから再ビルドします。手修正は指示前に **保存** してください。受付後に保存版が変わった場合は最新版を確認して送り直してください。会話と実行結果は Run ごとに残ります。再起動前に開始済みで結果が記録されていない指示は、履歴と進捗を確認してから改めて送ってください。

- **トークン使用量** のRun一覧で、Run IDや移行単位で絞り込み、開始日時やトークン合計で並び替えられます。Runを選ぶと、Run全体とカプセル別の入力・出力を確認できます。ハーネスは約0.5秒ごとにJunieのローカルログの追記を確認し、使用量が増えたら `run.json` に保存してSSEで配信します。再試行と再開分は同じカプセルに加算し、ビルド・チェッカーの自動修正とアンカー生成は工程別に集計します。入力合計の内訳として、通常入力、キャッシュ読み込み、キャッシュ作成を表示します。導入前のRunやJunieから使用量の報告がない場合は、記録のある分だけを表示します。

進捗デモでは5つのタブと台帳をサンプルデータで試せます。設定タブではモデルと推論の強さを選んで保存し、読み込み直すことができます。保存内容は新しい模擬Runに記録し、再開時にも保持します。候補は固定のサンプルで、Junieは起動しません。デモの設定はページ内だけに保持し、ブラウザーを再読み込みすると初期値に戻ります。実行タブでは最大5件ずつの模擬実行、待機取消、個別停止・再開と、進捗・エディタのRun切り替えを試せます。**進捗 → Junie に指示** では、指示の登録と区間終了時に反映される様子を確認できます。**エディタ** で編集を保存するか指示を送信すると、ページ内で Junie の更新と区間終了時の反映を順に再現します。

公式の Monaco Editor 0.57.0 から生成した配布ファイルとライセンスは、リポジトリと Python パッケージに同梱されています。clone した人も npm や Node.js の追加インストールは不要です。Monaco の配布ファイルを更新するときだけ、開発環境で `python tools/bundle_monaco.py` を実行します。

### コマンドから実行する

Windowsでは、リポジトリ内の`h.cmd`を短いランチャーとして使えます。仮想環境の有効化や`--config`指定は不要です。

```powershell
.\h.cmd p "メニュー"
.\h.cmd r "メニュー"
.\h.cmd s
```

`p`はprepare、`r`はrun、`s`はresumeです。resume時にRun IDを省くと入力を求めます。特定のRun IDを指定する場合は`.\h.cmd s <run-id>`とします。以下のCLI例も、仮想環境の実行ファイルを直接呼び出します。

指定内容の検証、コンテキスト作成、worktree作成だけを行う場合:

```powershell
.\.venv\Scripts\php-to-csharp-harness.exe prepare --config harness.local.toml --unit "メニュー"
```

Junieを起動して対象ファイルを移行する場合:

```powershell
.\.venv\Scripts\php-to-csharp-harness.exe run --config harness.local.toml --unit "メニュー"
```

`run`には`PATH`上のJunie CLIと移行先に対応する.NET SDKが必要です。ダッシュボードなしで起動する場合は対話ターミナルも必要です。既定ではJunie用作業フォルダに、移行先ファイルの親フォルダ、その隣の `inc`、`inc` より1階層上の `Libs` と `Extensions` を、worktreeに存在するものだけフォルダごとに同じ相対配置で取り込みます。たとえば `src/Web/Pages/Orders/Index.cshtml.cs` なら `src/Web/Pages/Orders/`、`src/Web/Pages/inc/`、`src/Web/Libs/`、`src/Web/Extensions/` です。移行先以外は参照専用で、初回移行時の内容を保存して再開・修正でも使います。Gitの管理情報は取り込みません。複数カプセルがある場合は、前の呼び出しで更新したファイルを次の呼び出しへ引き継ぎ、各呼び出し後にworktreeへ反映します。

Junieはカプセルの作業を終えると、作業フォルダに今回の起動専用の完了記録を残します。ハーネスが記録を検知するとJunieのセッションを自動で閉じ、編集をworktreeへ反映して次のカプセルへ進みます。最後のカプセルを反映した後はビルドに進みます。有効な記録がない状態でJunieを閉じた場合は、部分編集を保存して現在のカプセルを保留します。終了コードは診断用で、自動終了時にも非ゼロになる場合があります。完了記録はJunieの自己申告で、移行結果は最後にworktreeの差分で確認してください。

ダッシュボードから実行する移行、追加指示の反映、自動修正は、Junie CLIのACPモードを使います。作業フォルダーを初めて使うときはダッシュボードで信頼を確認します。Junieがコマンド実行などの許可を求めた場合も、同じ確認ダイアログで内容を読み、選択肢を返せます。閉じたダイアログは **Junie の確認を開く** から再表示できます。

既定ではACPの権限動作を変えません。`[junie].pinned_reference_reads = true` を指定し、JunieがACPのクライアント側読み取り (`fs/read_text_file`) を利用する場合は、現在のRunの登録済み資料に限り、ハッシュを照合してハーネスが直接読み取ります。絶対パスで対象を特定できない資料、変更された資料、範囲を指定せず上限を超えた読み取りは返しません。この経路はJunie自身のツール要求を自動許可するものではありません。ツール名・分類から実際の操作を確定できない要求、コマンド実行、書き込みなどは従来どおり確認します。作業フォルダーの信頼確認も残ります。Junieの版によっては、参照以外もクライアント側に読み取りを委ねる場合があります。利用中の版で移行先を読めなくなる場合は、この設定を無効にしてください。

`junie-input --config … --run-id …` の `junie_permission_counts` には操作の分類・理由別の累計だけが残り、確認本文やコマンド引数は保存されません。`pinned_reference_read` はハーネスから資料を返した回数であり、Junieのバージョンやモデルごとに操作モーダルが何件減るかを示す値ではありません。

ダッシュボードを使わない実行では、Junie CLIを端末で `--brave` 付きで起動します。Junieのファイル操作やコマンド実行ごとの承認は省略されます。初回のプロジェクト信頼確認は別の操作です。

Junie が ACP で利用できるモデルがないと応答した場合は、**今回のみ非対話モードで再試行** を選ぶと同じ作業フォルダーと指示で再試行します。この再試行には `--task` に対応した Junie CLI と、非対話モードで利用できるモデルが必要です。非対話モードでは、個別操作の許可確認はダッシュボードに表示されません。

全カプセルが完了すると、worktreeのルートを作業ディレクトリとしてビルドします。`[build].project` にアプリルートからの相対パス、またはアプリリポジトリ内の絶対パスで `.csproj`、`.sln`、`.slnx` を指定できます。worktree内のパスに変換してビルドするため、元のリポジトリには書き込みません。省略時はルートで `dotnet build` を実行します。

`run.json` の `build_attempt_seconds` には、`dotnet build` の呼び出しにかかった秒数を、失敗・中断・再実行も含めて順に記録します。ダッシュボードのビルド工程には前後のフックや移行対象の版の記録も含まれます。

進捗画面の **現在の処理** には、ビルドエラーの確認、修正資料の準備、Junieによる修正、修正結果の照合、再ビルドを分けて表示します。自動修正の回数・対象ファイル、現在の処理の経過時間、直前のビルド時間も確認できます。**直近の作業報告** はファイルの読み取り・検索・編集などの実際に届いた報告で更新し、プロセスの **稼働確認** では上書きしません。新しい報告が届かない間もその経過を表示し、既存の **停止**・**Junie に指示** から対応できます。ビルド失敗中はチェッカーへ進まず、修正後のビルド成功を待ちます。

### 独自チェッカーを指定する

ビルド成功後、チェッカーをworktreeのルートで実行します。`--checker-command` はコマンドの最後に置き、実行ファイル名と引数を続けて指定します。たとえば、アプリ側の `tools/check_migration.py` をWindowsで呼ぶ場合は次のようにします。

```powershell
.\.venv\Scripts\php-to-csharp-harness.exe run --config harness.local.toml --unit "メニュー" --checker-command py -3 tools/check_migration.py
```

`.\h.cmd r` や `.\h.cmd s` から使う場合は、`harness.local.toml` に設定します。CLIに指定したコマンドがTOMLより優先されます。指定を省略するとビルドで終了します。

```toml
[checker]
command = ["py", "-3", "tools/check_migration.py"]
max_repair_attempts = 2
# review_free_output_with_junie = true
```

チェッカーはプロジェクト共通の `[checker].command` で設定します。CLIの `--checker-command` が指定されていれば、CLIを優先します。どちらも未指定ならチェッカーは実行しません。`{target}` を引数に渡すと、共通のチェッカーで対象ファイルを判別できます。`max_repair_attempts` はRun全体の共通上限です。

チェッカーと `[scripts]` の通常コマンドには、実行時に絶対パスへ展開する次の別名を指定できます。Run IDを設定ファイルに書く必要はありません。ダッシュボードの引数欄や `--checker-command` でも使えます。

| 別名 | 展開先 |
| --- | --- |
| `{build_project}` | そのRunのworktree内にある `[build].project` のファイル。使用時は `[build].project` の設定が必要です。 |
| `{target}` | そのRunのworktree内にある移行先ファイル。`targets` が複数なら設定順の先頭を使います。 |
| `{worktree}` | そのRunのworktreeのルートディレクトリ。 |

```toml
[checker]
command = ["py", "-3", "tools/check_migration.py", "--project", "{build_project}", "--target", "{target}"]

[scripts]
after_build = [["py", "-3", "tools/export_results.py", "{build_project}", "{target}"]]
```

引数の一部にも使えるため、`"--project={build_project}"` や `"{worktree}/Pages/Menu.cshtml"` も指定できます。空白を含むパスも1つの引数として渡します。展開先はビルド・検証に使うworktreeで、Junieが直接編集する `agent-workspace` は指定しません。worktree作成前の `before_prepare` では使用できません。仮C#取り込みの `@copy-migration-draft` は従来のコピー元・コピー先の指定方法を使い、別名は展開しません。

### ビルドエラーとチェッカーの指摘を自動修正する

`[checker].review_free_output_with_junie = true` を指定すると、形式未対応のチェッカー出力を自動修正へ渡さず、別のテキスト専用 ACP セッションで Junie の参考判定を得ます。既定は `false`（従来の挙動）です。対象は `checker.log` の UTF-8 出力（最大 32 KiB）で、設定を有効にするとその内容が Junie のモデルサービスに送信されます。機密情報が出力されるチェッカーでは有効にしないでください。対象リポジトリやファイルはセッションに渡さず、ツール要求はセッションを中止します。ただし ACP は OS のサンドボックスではありません。判定・根拠行・ログの SHA-256 を `run.json` の `checker_advisory` に保存します。参考判定だけを有効にした場合は「情報のみ」でも合格にせず、判定不能・接続不可の場合も確認待ちです。通常の構造化された指摘はこの参考判定の対象外です。

`[junie].review_script_output = true` を指定すると、設定済みの工程スクリプトにも同じ形式の参考判定を適用します。工程ログ全体ではなく各コマンドの今回の出力だけを送信し、コマンド識別用ハッシュ・ログ範囲・終了コード・判定を `script_advisories` に直近100件まで保存します。一度だけ実行するスクリプトは、参考判定を停止しても成功済みのコマンドを再実行しません。既定は `false` です。参考判定だけを有効にした場合は、既存の終了コードによる続行・停止を変更せず、自動修正や再実行にも使いません。

`[junie].apply_output_decisions = true` を追加すると、上記の参考判定を工程に反映します（既定では無効、チェッカーまたはスクリプトの参考判定を別途有効化する必要があります）。続行には、終了コード 0 に加え、本文の全行を根拠にした Junie の合格判定と、ハーネスが照合できる明確な成功表現が必要です。問題や注記の混在、不明な出力、接続失敗、対象版またはログが変わった場合は確認待ちです。内容が曖昧なときは自動で合格にしません。

準備前・準備後・移行前の自作スクリプトが正常終了し、ログで照合できるソース識別子を Junie が申し送りに指定した場合、同じ Run・コマンド・ログ・対象版に限り、移行開始時の手がかりとして識別子だけを渡します。ログの指示や原文全体を後続の編集セッションへ移さず、完了や編集権限の根拠にも使いません。対象版と保存した出力が一致する一度だけの処理は、コマンドを再実行せず判定を再開できます。worktree 作成前に停止した準備は再開せず、原因を確認して新しく準備します。

チェッカーと `after_build` の既存形式の診断は、対象ファイルまで照合できる場合に既存の修正経路を使います。自由形式の指摘も根拠から調べる場合は、参考判定・工程への反映に加え `[junie].ground_output_repairs = true` を指定します（既定は無効）。これはログだけでなく、関係する固定済み PHP と現行 C# の限られた抜粋を、別のテキスト専用 ACP セッションでモデルサービスに送る設定です。送信できないソースには有効にしないでください。

この追加設定では、繰り返し実行されるビルド前後・チェッカー前後のスクリプトとチェッカーの問題を対象に、固定原文と現在の移行先の両方で根拠を照合します。対象を特定できない、根拠または版が合わない、結果が曖昧な場合は確認待ちです。修正は既存の移行範囲と回数上限・停滞検知の中で実行し、ビルドから再検証します。準備・移行前のスクリプト、明示的な検証のみの依頼、ログ中の任意コマンドはこの自動修正の対象外です。

別 ACP セッションによるログ判定とソース照合にも、その Run に保存した Junie モデルの指定を使います。指定がなければ通常どおり Junie の既定に任せます。指定したモデルや ACP に接続できない場合は判定不能として扱い、別モデルで確認済みとはしません。

`max_repair_attempts` は、1つのRunで実行するJunieのビルド・チェッカー修正の合計上限です。既定値は `2` で、`0` は自動修正を無効にします。ビルドでは、移行先を指すC#・Razorのコンパイラエラーを修正し、再ビルドします。大量の同種エラーは全行を検査してまとめ、修正前の全文ログを `build-before-repair-N.log` に保存します。修正が進まない場合、異なる指摘が多すぎる場合、移行先外の指摘、依存関係などのエラーは人が確認します。

チェッカーは合格なら出力なしで終了コード `0`、修正や確認が必要なときは診断を出力して正の終了コードを返してください。標準出力と標準エラーを合わせた応答全体が UTF-8 の **特に気になる点はありません。** だけの場合も、問題なしとして自動修正を終了します（前後の空白・改行・先頭のBOMは許容し、プロセスの中断・起動失敗は除きます）。この明示的な成功応答は正の終了コードでも受け付け、実際の終了コードは記録に残します。JSONの値・引用・説明文の一部にある成功文言は合格扱いにしません。UTF-8 の `ルールID ファイル:行 warning: メッセージ`、`ルールID ファイル:行 error: メッセージ`、または次の6項目形式の指摘がある場合は、終了コード `0` でも指摘を優先します。指摘のあった移行先に絞って Junie が修正し、指摘ごとに人が承認できます。

```text
ファイル: Pages/Menu.cshtml.cs
対　処: 合計に送料を加算する
内　容: 合計に送料を含めてください
行番号: 12
コード: return subtotal;
備　考: 元PHPの送料加算を確認してください
```

6項目形式では、`ファイル` から始まるまとまりを1件の指摘として扱います。項目名の中やコロン前後の半角・全角空白、タブ、半角・全角コロンの違いを許容します。ファイルにはworktree基準のパス、行番号には1始まりの整数を指定し、対処・コード・備考の値は空でも構いません。対処・内容・コード・備考は複数行に対応し、その情報をまとめてJunieに渡して修正します。複数件は次の `ファイル:` から続けて出力できます。

JSON や自由記述、読み取れない項目を含む場合は、終了コード `0` でも Junie がチェッカー出力全体を読み、移行元と移行先を照合して修正の要否を判断します。この場合、編集できるのは設定済みの移行先です。正の終了コードで空の出力、読み取れない文字コード、64 KiB を超える出力は人の確認に回します。従来 `PASS` などの独自の成功ログを出力していたチェッカーは、合格時を無出力にするか、上記の成功応答だけを出力するよう変更してください。件数や実行時間などは別ファイルへ保存します。

自動修正の前に、移行先の現行版をworktreeからJunie用フォルダへ同期します。中断からの再開では、指摘と移行先が保存時と一致する下書きを引き継ぎます。修正前のチェッカー出力は `checker-before-repair-N.log`、直近の結果は `checker.log`、試行履歴は `run.json` に残ります。対応形式の指摘は行番号が変わっても識別し、前回の同じ工程の修正対象から指摘の種類が減り、新しい指摘が混じらない場合は、残り回数内で修正を続けます。同じ集合のまま、解消済みの指摘の再発、残った指摘と新しい指摘の混在は人の確認に回します。JSON・自由記述・サマリーが混じった出力は、空白を正規化した全文が繰り返された場合に止めます。指摘の一部が残っていても全文が変わっていれば、残り回数内で修正を続けます。上限、対象外のファイル、Junieの未完了や変更なしでも、その理由を記録します。

移行時は現在のカプセルと境界資料、修正時は元のPHP全カプセル・診断・追加指示を、JSON化後24,000 UTF-8バイト以内なら必須ルールとまとめて起動時に渡します。読み込みの往復を減らし、Junieにすべての診断をまとめて検討させます。上限を超える場合は一部を切り捨てず、全ファイルの参照に戻ります。元ファイル・ログは保持し、現行の移行先は毎回読み直します。本文はガイドラインファイルで渡すため、Windowsのコマンド引数は長くなりません。

修正後もビルド→`after_build` のテスト等→独自チェッカーの順に毎回実行します。テストは `[scripts].after_build` に設定でき、失敗するとチェッカーへ進まずログを残します。たとえばビルド済みテストプロジェクトには `dotnet test --no-build` を指定でき、同じソースの二重ビルドを避けられます。修正回数の上限は進捗があってもリセットしません。

ダッシュボードの **チェッカー出力を確認** には、自動修正が止まった理由と次の操作が日本語で表示されます。**チェッカー出力** では元の出力を表示・ダウンロードでき、**詳細ログ** では終了コードや診断の原文を確認できます。必要に応じて **Junie への追加指示** を入力し、**指示を送って再開** を選ぶと、Junie が出力と指示を確認してから再ビルドします。**エディタで手修正** から移行先を編集して再開することもできます。CLI では同じ Run ID で `resume` を実行できます。チェッカーの段階から再開する場合も先にビルドし、現在のビルドが成功してからチェッカーを実行します。修正回数と指摘の履歴は維持します。CLIでのみチェッカーを指定した場合は、`resume` にも `--checker-command` を指定します。

CLIでチェッカーを上書きしたRunを台帳で確認するときは、TOMLのプロジェクト共通コマンドが検証時と同じなら、実行に使用したコマンドで検証結果を照合します。TOMLの既定や実行コマンドが変わった場合は再検証が必要です。チェッカーのファイル内容の変更は自動検出しないため、変更時は明示的に再検証してください。この判定に使うTOMLの既定値は、チェッカーだけの再開も含め、CLIで上書きして検証したときに保存します。旧版でチェッカーだけを再開し、既定値の出所を確認できない記録は、CLI上書きの引き継ぎに使わず、必要に応じて再検証してください。

ログが65,536バイトを超える場合や、対応形式の指摘が8,000文字を超える場合は、自動修正を保留し、元の `checker.log` を残します。手動レビューではこれらの上限に関わらず、読み取れた指摘を一覧できます。

### 指摘を「問題なし」として記録する

`review` で最新の指摘とそのIDを確認します。差分とチェッカーの出力を確認し、偽陽性などと判断した指摘のIDと理由を指定します。

```powershell
$runId = Read-Host "Run ID"
.\.venv\Scripts\php-to-csharp-harness.exe review --config harness.local.toml --run-id $runId
$findingId = Read-Host "Finding ID"
.\.venv\Scripts\php-to-csharp-harness.exe review --config harness.local.toml --run-id $runId --accept $findingId --reason "共通関数に委譲していることを確認済み"
.\.venv\Scripts\php-to-csharp-harness.exe resume --config harness.local.toml --run-id $runId
```

判断は `run.json` に保存します。再開するとビルドとチェッカーを再実行し、同じファイル内容に対する承認済みの指摘だけが残っている場合は `checker_accepted` として完了します。チェッカーが返した終了コードはそのまま残ります。行・列のずれを許容しますが、対象ファイルを編集した場合は再確認が必要です。新しい指摘や解釈できない出力が残る場合は通常の確認フローに戻ります。同じIDの指摘が複数ある場合は、区別できるようにチェッカーのメッセージを整えてください。

### ブラウザーで進捗と指摘を確認する

```powershell
.\.venv\Scripts\php-to-csharp-harness.exe run --config harness.local.toml --unit "メニュー" --dashboard
```

ターミナルに表示された `http://127.0.0.1:...` のURLを開きます。完了後を含む保存済みの実行は、次のコマンドで開きます。Windowsでは `.\h.cmd v` も使えます。

```powershell
.\.venv\Scripts\php-to-csharp-harness.exe view --config harness.local.toml --run-id RUN_ID
```

`view` と `resume --dashboard` は保存された結果を表示します。再開するときは画面の **同じ実行を再開** を選びます。`--checker-command` を指定するときは、コマンドと引数を末尾に置きます。

ビルド失敗時は **ビルド失敗を確認** からエラー箇所とビルド出力を確認できます。**Junie への修正指示** を入力して再開すると、Junie の修正後に同じ Run を再ビルドします。**移行対象ファイルを編集** でこの Run の作業ツリーに変更を加えることもできます。指示と編集を一緒に送ると、編集を保存してから Junie が修正します。画面内では UTF-8・8 MiB 以下の移行対象を一度に1ファイル編集できます。

人の確認待ちになるとモーダルが開きます。指摘を選んで判断理由を入力し、**問題なしとして記録**を押します。必要な指摘を記録したら、**同じ実行を再開**を押します。再開後にJunieが許可を求めた場合も、確認ダイアログに表示されます。

画面はPython標準ライブラリのHTTPサーバーで配信し、進捗の受信にはSSEを使います。URLは起動した端末で利用できます。ブラウザーが再接続すると、同じサーバーの直近100件の範囲で未受信のイベントを再送します。実行結果と判断理由は `run.json` に残ります。画面を終了するときは、ハーネスのターミナルで Ctrl+C を押します。

工程の経過時間はRunに保存し、再開時に加算します。停止中の待ち時間は除き、時間記録がない旧Runと人の確認は「未計測」と表示します。Junieのツール実行・応答完了を通知し、起動時と稼働中の約3秒ごとに状況を通知します。Junieの稼働確認には最後のイベントからの経過秒数も表示します。生存表示は処理の進展や応答完了を保証するものではありません。

**停止** はJunie、ビルド、チェッカー、自作スクリプトに適用され、自動修正の中断だけでは修正回数を消費しません。worktree作成中はGitの完了を待って停止します。worktree作成前に準備を止めた場合は、実行タブから準備をやり直してください。

指摘が残ったら、**判断が必要です** または指摘の行を押すと確認モーダルが開きます。**判断待ち** で未判断の指摘だけを表示できます。チェッカーの出力から取得できたファイル名と行番号は、モーダルの **指摘箇所** に表示されます。

### Diff Viewerで差分を確認する

ダッシュボードでDiff Viewerを使う場合は、**プロジェクトの詳細設定** の **差分ビューアーのHTML** に単一HTMLを指定します。アプリルートからの相対パス、またはアプリ外の絶対パスが使えます。たとえば `tools/dist/index.min.html` を指定します。HTMLの空欄や **使用しない** の選択で比較とアンカー生成が無効になり、移行と検証は実行できます。

worktreeの準備後は、進捗画面の **比較ツールを開く** でその時点のソースを確認できます。左には準備時に保存した移行対象のPHP、右には最新の移行先を表示します。共通の参考PHPは移行時の資料として使います。Junieの移行・修正中は保存済みの編集中ファイルを優先し、未生成のファイルは空欄になります。比較は取得時点のコピーで、開いた後の編集は自動反映されません。確認待ちのモーダルからも同じ操作ができます。

確認モーダルから開くと、選択中の指摘の報告行を右ペインに表示します。判断待ちのときにダッシュボード上部から開くと、最初の未判断の指摘を表示します。行番号が取れない場合や、報告行が比較対象の範囲外の場合は通常の位置で開きます。

**比較ツールを開く** を押すと、Diff Viewerが別タブで開き、取得時点の比較データを読み込みます。JSONが必要な場合は、進捗画面の **ワークスペースJSONを保存** からダウンロードできます。別タブを開けない場合は、ダッシュボード内のダイアログで比較できます。同じJSONを実行ディレクトリの `review-snapshots/<ID>.json` に保存します。実行終了後も、保存済みJSONをローカルのDiff Viewerでインポートして確認できます。スナップショットにはソース全文が含まれ、Viewerで扱うのはそのコピーです。

公開の進捗デモでは、同じ画面内で模擬データの比較とJSONのダウンロードを試せます。「人の確認待ち」になったら、画面上部と確認モーダルのどちらから開いても右ペインに指摘行を表示します。デモHTMLをブラウザーで直接開いた場合は、ダウンロードされたJSONをViewerの **インポート** から読み込みます。

#### Razorページに複数の指摘がある例

サンプルのチェッカーが次の順で指摘を出した場合、比較ツールは操作に応じて右ペインの表示位置を選びます。行番号は各ファイル内の番号です。

```text
MIG401 Pages/Review.cshtml.cs:5 warning: Confirm PageModel return value.
MIG402 Pages/Review.cshtml:3 warning: Confirm rendered result.
```

| 操作 | 右ペインの表示位置 |
| --- | --- |
| 2件とも未判断の状態で、画面上部から開く | `Pages/Review.cshtml.cs` の5行目 |
| 確認モーダルで `MIG402` を選んで開く | `Pages/Review.cshtml` の3行目 |
| 確認モーダルで `MIG401` を選んで開く | `Pages/Review.cshtml.cs` の5行目 |
| `MIG401` を **問題なしとして記録** し、画面上部から開く | `Pages/Review.cshtml` の3行目 |

### Junieでアンカー付きの比較JSONを作る

差分ビューアーを有効にして、ダッシュボード上部または指摘の確認モーダルで **比較ツールを開く** の右にある `▾` から **Junieで対応行を提案して開く** を選びます。**アンカーの参照JSON（任意）** に、手動アンカー付きのワークスペースJSONのパスを1行に1つ入力してください。Junieは各ファイルの先頭12件までの手動アンカーを手本にします。空欄なら同じRunの確認済み対応例を使います。絶対パス、または設定ファイルの場所からの相対パスが使えます。TOMLの `[diff_viewer].anchor_reference` は配列で指定でき、従来の単一パスも読み込めます。指定ファイルがない・JSONが不正な場合はエラーになり、自動参照には切り替えません。Junieが操作の許可を求めたら、進捗画面の確認ダイアログで回答します。生成が完了すると、別タブのDiff Viewerに結果が表示されます。JSONは **ワークスペースJSONを保存** からダウンロードできます。

コマンドから生成する場合はRun IDを指定します。手動アンカー付きのワークスペースJSONを明示して使う場合は、`--reference` をファイルごとに指定します。

```powershell
.\.venv\Scripts\php-to-csharp-harness.exe anchors --config harness.local.toml --run-id $runId --reference .\orders.workspace.json --reference .\products.workspace.json
```

アンカー生成は、起動するJunieのヘルプで `--task` 対応を確認し、対応していれば非対話モードを優先します。このモードでは操作ごとの許可確認は表示されません。非対応なら従来の起動方法を使い、CLIからの実行には対話端末が必要です。

Junieは対応行の例と今回のスナップショットのコピーを読み、行の対応を提案します。ハーネスは行番号の範囲・重複・順序を検証し、アンカー付きのワークスペースJSONを `review-snapshots` に新規保存します。元のソース、参照JSON、既存のスナップショットはそのままです。

コマンドが表示するJSONをDiff Viewerのワークスペース **インポート** から開き、提案された対応行を確認・調整します。

### 中断・失敗から再開する

ダッシュボードの **実行** タブで対象Runを探し、**再開** を押します。Windowsの端末からは `.\h.cmd s` も使えます。全カプセルの移行後に停止した実行は、ビルドから再検証します。失敗の詳細はRunの `build.log` や `checker.log` を確認してください。ログは直近の試行の内容に更新されます。通常のCLIから再開する場合は次のコマンドを使います。

```powershell
$runId = Read-Host "Run ID"
.\.venv\Scripts\php-to-csharp-harness.exe resume --config harness.local.toml --run-id $runId
```

Junieがステップ上限に達した場合、ダッシュボードから同じRunを再開できます。端末での実行では、同じ対話画面で続きを依頼できます。ハーネスがCtrl+Cを受け取った場合も、部分編集と実行記録を保存します。`resume`は、完了済みのカプセルを飛ばし、新しいJunieセッションに未完了カプセルと編集済みの対象ファイルを渡します。Junieは原文と保存済みの編集を照合して残りの移行を進めます。再開時にworktreeの対象ファイルが記録後に変更されている場合は、上書きせず停止します。

`[junie].max_steps`は任意の正の整数です。未設定の場合は`--max-steps`をJunieに渡しません。これは1つのタスクの手順数上限で、トークン数や料金の上限ではありません。複数カプセルでは呼び出しごとに適用されます。クォータ切れなどJunie側で続行できない場合は、利用枠が戻るまで待つ必要があります。Junieがモデルサービスとの通信失敗を確定したときは、同じ作業場所で1秒、3秒の待機を挟んで最大2回再試行します。復旧しない場合は接続を確認して同じRunを再開できます。

設定タブの「プロジェクトの詳細設定」→「Junieで使うモデル」でモデルを選んで保存できます。候補はインストール済みJunieの `list-models` から取得し、取得できない場合は代表的なモデルの別名を表示します。候補外のモデルIDはTOMLで `[junie].model = "モデルID"` と指定でき、フォームでも指定値を保持します。「Junieの既定モデル」を選ぶとモデル指定を省略します。実行時は [Junieの `--model` オプション](https://junie.jetbrains.com/docs/parameters.html) に渡すため、利用にはそのモデルに対応したJunieのログイン・契約が必要です。

推論の強さは同じ設定欄で選べます。対応値はモデルごとに切り替わり、指定しなければ **モデルの既定値** を使います。TOMLでは `[junie].effort = "high"` のように指定します。指定できる値は `none`・`minimal`・`low`・`medium`・`high`・`xhigh`・`max` で、`model` の指定も必要です。実行時は [Junieの `--effort` オプション](https://junie.jetbrains.com/docs/junie-cli-model-selection.html) に渡します。 ダッシュボード実行・ルール相談では、ACPセッションでも指定値を確認し、必要なら初回送信前に設定し直します。タイムアウトや未反映時は同じ値を一度だけ再設定し、確認できなければ指示を送らず停止します。設定画面ではJunieが対応を報告した値だけ新しく選べます。保存済みの非対応値は勝手に変更せず、選び直しを案内します。

モデルと推論の強さは新しく準備するRunに保存し、移行・ルール確認・自動修正・追加指示・比較アンカー生成と、そのRunの再開に引き継ぎます。設定を変更しても準備済みRunのモデル・推論の強さは変わりません。モデル記録のない旧版のRunは現在のモデル設定を使い、推論の強さの記録がないRunでは強さを指定しません。既定モデルやモデルの別名が指す実際のバージョンはJunie側の設定に従います。

自動修正の中断とモデルサービスの通信失敗で終了した試行は、ビルド・チェッカーの自動修正回数に含めません。カプセル作成に失敗した場合は、設定を直して新しく実行します。

実行データとコンテキストには利用者のソースが含まれる場合があります。ローカルで適切に管理してください。設定範囲の指定は、JunieのOSレベルのファイルアクセス制御ではありません。
